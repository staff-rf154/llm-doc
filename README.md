# RAG-ассистент по внутренней документации

Локальная RAG-платформа для ответов на вопросы по корпоративной документации:
FastAPI + Qdrant + Ollama + SQLite. Разворачивается в Docker Compose, работает на
CPU без GPU. Поддерживает многоформатную индексацию, гибридный поиск
(dense + BM25), переранжирование, синонимы, сферы деятельности, исправления и
уроки администратора, автообучение, генерацию проверочных вопросов, ролевой
доступ и сквозной супер-тест.

Репозиторий проекта:
[github.com/staff-rf154/llm-doc](https://github.com/staff-rf154/llm-doc).
Генерация ответов — локальная LLM `qwen2.5:3b-instruct` через Ollama.

## Как это работает

```
data/docs/** ──► loaders.py ──► чанкинг ──► multilingual-e5-base (+ BM25)
                                                    │
                                                    ▼
                              Qdrant: docs_v<timestamp> ──alias──► "docs"
                                                    │
 вопрос ──► исправления ──► синонимы ──► уроки ─────┤
                                                    ▼
                                   retrieval + rerank + LLM + цитаты
                                                    │
                                                    ▼
                     app.db: вопрос, ответ, источники, оценка, request_id
```

1. **Источники.** Файлы берутся из `data/docs` (включая подпапку `upload`).
   Каталог доступен на запись: загруженные через кабинет документы сохраняются в
   `data/docs/upload`.
2. **Загрузка.** `loaders.py` читает PDF (pypdf), DOCX/PPTX, ODT/ODS/ODP,
   XLSX, MS Office 2003 (`.doc/.xls/.ppt` через `catdoc`, `xls2csv`, `catppt`),
   EPUB, HTML, CSV/TSV, JSON/XML/YAML и другие текстовые форматы. PDF читается
   постранично, поэтому чанк помнит страницу.
3. **Чанкинг.** `ingest.split_text` режет текст `RecursiveCharacterTextSplitter`
   с перекрытием `CHUNK_SIZE` / `CHUNK_OVERLAP`; страницы чанкуются раздельно.
   При `PARENT_CHILD_ENABLED=1` дополнительно собираются крупные родительские
   фрагменты, а в ответ попадает их полный текст (см.
   [Родительские фрагменты](#родительские-фрагменты)).
4. **Эмбеддинги.** `vectorstore.embed_passages` кодирует чанки моделью
   `intfloat/multilingual-e5-base` (префикс `passage: `), запросы — с префиксом
   `query: `; векторы нормализованы, метрика косинусная.
5. **Хранилище.** Qdrant: версионированная коллекция `docs_v<YYYYmmdd-HHMMSS>`,
   имя `docs` — алиас, через который идёт весь поиск.
6. **Расширение запроса.** `synonymdb.expand` подставляет синонимы из
   `data/synonyms/synonyms.db`; варианты ищутся в Qdrant и объединяются по
   `(source, chunk)`.
7. **Исправления.** Таблица `corrections` в `app.db` и коллекция `corrections` с
   эмбеддингами вопросов: при достаточной схожести исправленный ответ отдаётся
   вместо сгенерированного.
8. **Retrieval + генерация.** `rag.retrieve` берёт `RETRIEVE_TOP_K` фрагментов,
   `rag.ask` собирает промпт с цитатами и обращается к LLM (Ollama или внешний
   OpenAI-совместимый API). Флаг `grounded` показывает, был ли ответ отказом.
   В режиме parent-child поиск идёт по дочерним чанкам, а в промпт после
   дедупликации подставляется родительский текст.
9. **Сайты.** Страницы сайтов пишутся в ту же активную коллекцию с источником
   `web/<host>/<path>` и URL в payload.
10. **Журнал.** Каждый вопрос и ответ пишутся в `app.db` вместе с пользователем,
    временем, источниками, ссылкой и оценкой.

## Требования

- Docker + Docker Compose v2.
- ~5 ГБ RAM для `qwen2.5:3b-instruct` + эмбеддингов; ~8 ГБ для 7B.
- ~1 ГБ на диске под веса эмбеддингов (`./app/.cache`).
- От 8 CPU-ядер для комфортной индексации (параллелизм настраивается).
- Для обхода сайтов — исходящий HTTPS и вежливый `User-Agent`.
- Для MS Office 2003 вне Docker-образа нужны `catdoc`, `xls2csv`, `catppt`
  (пакет `catdoc`); в образе они уже установлены.

## Быстрый старт

```bash
cp .env.example .env

# задать администратора (создаётся при первом старте)
# ADMIN_USERNAME=admin
# ADMIN_PASSWORD=сильный-пароль
# APP_TITLE=База знаний

# 1. документация в data/docs
# 2. поднять qdrant + ollama + api
make up

# 3a. первичная индексация из CLI
make ingest

# 3b. либо индексация в фоне, поиск продолжает работать
make reindex

# 4. открыть чат и войти
# http://localhost:8091/
```

При первом старте автоматически создаются БД:

| БД | Путь | Что хранит |
|----|------|------------|
| состояние индексации | `data/index_state/index.db` | срезы прогресса и незавершённые запуски |
| пользователи и журнал | `data/app/app.db` | учётные записи, сессии, вопросы и ответы, оценки, исправления, уроки, направления, память вопросов |
| настройки | `data/settings/settings.db` | все параметры кабинета и служебные ключи |
| синонимы | `data/synonyms/synonyms.db` | словарь синонимов |
| промты | `data/prompts/prompts.db` | стартовые вопросы чата |

Прогресс фоновой индексации: `make reindex-status` или `GET /reindex`.
Кабинет администратора: `http://localhost:8091/admin`.

## Пользователи и авторизация

- Логин/пароль, сессия в HttpOnly cookie `sid` (срок 14 дней).
- Пароли — PBKDF2-SHA256, 200 000 итераций, индивидуальная соль.
- Роли: `user` (чат и оценки), `admin` (кабинет администратора), `system`
  (скрытый служебный пользователь: дополнительно управляет сферами деятельности
  и моделями).
- Первый администратор создаётся при первом старте из `ADMIN_USERNAME` /
  `ADMIN_PASSWORD`, только если таблица пользователей пуста.
- Системный пользователь создаётся автоматически. Если `SYSTEM_PASSWORD` пуст,
  пароль генерируется и сохраняется в `data/app/system_password.txt`.
- Без входа недоступны `/chat`, `/ask`, `/api/rate/*` и `/api/admin/*`.

```bash
curl -s -c cookie.txt -X POST localhost:8091/api/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"..."}'

curl -s -b cookie.txt localhost:8091/api/me
curl -s -b cookie.txt -X POST localhost:8091/api/logout
```

Таблицы `data/app/app.db`:

| Таблица | Содержимое |
|---------|------------|
| `users` | `id`, `username`, `salt`, `password_hash`, `role`, `active`, `created_at` |
| `sessions` | `token`, `user_id`, `created_at`, `expires_at` |
| `requests` | вопрос, ответ, `grounded`, `corrected`, источники, `latency_ms`, `origin`, `created_at` |
| `ratings` | `request_id`, `vote` (`up`/`down`), `comment`, время |
| `corrections` | вопрос, ответ, документ, страницы, статус, результат сверки |
| `lessons` | тема, вопрос, ответ, ключевые моменты, статус, число срабатываний |
| `training_log` | журнал автообучения из исправлений и автоуроков |
| `domains` | направления: инструкция, возможности, категории, терминология, примеры, параметры |
| `request_evals`, `answer_issues` | эвристические оценки ответов и найденные проблемы |
| `question_topics`, `topic_requests` | темы вопросов и их связь с запросами |
| `generated_questions` | память сгенерированных вопросов, векторы, кластеры и почти-дубли |

## Настройки

**Отдельная база настроек.** Все параметры кабинета хранятся в
`data/settings/settings.db` (переменная `SETTINGS_DB`), независимо от `app.db`.
При первом запуске значения разово переносятся из старой таблицы `settings`.
Служебные ключи (название, активная сфера, список сайтов и т. п.) — там же.

**Название базы знаний.** По умолчанию берётся из `APP_TITLE`; пока админ не менял
название, используется значение из `.env`. Кнопка «Вернуть из .env» сбрасывает
переопределение.

**Параметры модели и пайплайна.** Любой параметр можно переопределить из кабинета:
значение попадает в `settings.db` и применяется сразу, кнопка «Сбросить» возвращает
значение из `.env`. Инфраструктурные параметры (порты, каталоги, адреса, коллекции)
показаны в группе «Инфраструктура (только чтение)».

| Группа | Параметры |
|--------|-----------|
| Генерация | `LLM_MODEL`, `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_TEMPERATURE`, `LLM_MAX_TOKENS`, `SSE_HEARTBEAT` |
| Поиск и чанкинг | `RETRIEVE_TOP_K`, `CORRECTION_MATCH_THRESHOLD`, `CORRECTION_OVERLAP_WORDS`, `CORRECTION_EXAMPLES`, `CORRECTIONS_COLLECTION`, `SYNONYMS_MAX_VARIANTS`, `SYNONYMS_CACHE_TTL`, `SYNONYMS_SEED_ON_START`, `EMBEDDING_MODEL`¹, `E5_QUERY_PREFIX`¹, `E5_PASSAGE_PREFIX`¹, `EMBED_BATCH`, `EMBEDDER_DEVICE`, `CHUNK_SIZE`¹, `CHUNK_OVERLAP`¹ |
| Поведение ответа | `PROMPTS_MAX`, `SYSTEM_PROMPT`, `PROMPTS_CACHE_TTL` |
| Гибридный поиск | `HYBRID_SPARSE`, `SPARSE_MODEL`¹, `HYBRID_CANDIDATES`, `HYBRID_FUSION` |
| Переранжирование | `RERANKER_ENABLED`, `RERANKER_MODEL`, `RERANKER_CANDIDATES`, `RERANKER_TOP_K`, `RERANKER_MAX_LENGTH`, `RERANKER_BATCH`, `RERANKER_DEVICE` |
| Загрузка документов | `UPLOAD_MAX_MB`, `UPLOAD_URL_TIMEOUT` |
| Индексация | `INGEST_WORKERS`, `INGEST_BATCH_SIZE`, `INGEST_CHECKPOINT_EVERY` |
| Обучение | `LESSONS_MAX`, `LESSONS_MIN_SCORE`, `LESSONS_COLLECTION`, `TRAINING_FROM_CORRECTIONS` |
| Сайты и обход | `WEB_CRAWL_MAX_PAGES`, `WEB_CRAWL_TIMEOUT`, `WEB_CRAWL_DELAY_MS`, `WEB_CRAWL_RESPECT_ROBOTS`, `WEB_CRAWL_USER_AGENT`, `DOCS_BASE_URL` |
| Автообучение | `AUTOLEARN_*`, `QUESTIONGEN_*` (включая `VARIANTS`, `SIM_THRESHOLD`, `DEDUP_THRESHOLD`, `SIM_LIMIT`), `BOOTSTRAP_*` |
| Инфраструктура (только чтение) | `APP_DB`, `SETTINGS_DB`, `QDRANT_URL`, `QDRANT_COLLECTION`, `QDRANT_API_KEY`, `INDEX_STATE_DB`, `DOCS_DIR`, `UPLOADS_DIR`, `EVAL_DIR`, `PROMPTS_DB`, `SYNONYMS_DB`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `DOMAIN_PROFILE`, `EMBED_DIM` |

¹ «Требует переиндексации»: вступит в силу со следующей индексацией, о чём сообщает
API в поле `requires_reindex`.

**Приоритет настроек:** настройки активной сферы деятельности > локальные значения
из `settings.db` > значения из `.env` / `config.py`.

**Проверка согласованности.** Перед сохранением сервер проверяет зависимости:

- `CHUNK_OVERLAP` меньше `CHUNK_SIZE`;
- при `HYBRID_SPARSE` задан `SPARSE_MODEL`;
- при `RERANKER_ENABLED` задан `RERANKER_MODEL`;
- `QUESTIONGEN_SOURCES` — только из `docs, topics, domain`;
- диапазоны температур и порогов (0–2 и 0–1);
- предупреждения, если `RETRIEVE_TOP_K > HYBRID_CANDIDATES`,
  `RERANKER_TOP_K > RERANKER_CANDIDATES` или
  `RERANKER_CANDIDATES > HYBRID_CANDIDATES`;
- для моделей e5 префиксы должны быть `query: ` и `passage: `.

## Модели и управление ими

Вкладка «Модели» (только `system`) управляет генеративной моделью и моделями поиска.

**Модель генерации (Ollama).** Кнопки:

- **Скачать** — `pull` модели по имени, прогресс в фоне;
- **Выбрать** — назначить активную модель (`LLM_MODEL`);
- **Выгрузить** — освободить память (`keep_alive=0`), модель остаётся на диске;
- **Удалить** — удалить модель с диска (активную удалить нельзя).

**Модели поиска (Hugging Face).** Для типов «эмбеддинги», «reranker» и «BM25
(sparse)» можно скачать модель, выбрать её и удалить из кэша. Смена модели
эмбеддингов требует переиндексации. Кэш — `HF_HOME`.

**Устройство вычислений.** `EMBEDDER_DEVICE` и `RERANKER_DEVICE`: `auto` (CUDA при
наличии, иначе CPU), `cpu`, `cuda`. Фактическое устройство видно в `/health` и на
вкладке «Модели».

## GPU: NVIDIA и Vulkan

Базовая сборка — CPU (`torch` из `download.pytorch.org/whl/cpu`). Для GPU есть
override-файлы compose, базовый запуск не меняется.

**NVIDIA (CUDA).** Нужны драйвер NVIDIA и `nvidia-container-toolkit` на хосте.

```bash
docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d --build
```

`docker-compose.gpu.yml` пересобирает образ с CUDA-сборкой torch и выдаёт GPU
контейнерам `app` и `ollama`. После запуска можно выбрать `EMBEDDER_DEVICE=cuda`
(или оставить `auto`).

**Vulkan / встроенная графика (Intel, AMD).** LLM-бэкенд получает доступ к
`/dev/dri`:

```bash
docker compose -f docker-compose.yml -f docker-compose.vulkan.yml up -d
```

Vulkan полезен только для LLM; модели поиска на torch Vulkan не используют.
Сборку можно переопределить переменными `BASE_IMAGE` и `TORCH_INDEX_URL`.

## Сфера деятельности компании

Проект не привязан к одной отрасли. Вкладка **«Сфера деятельности»** (роль
`system`) хранит направления, а карточка в «Настройках» переключает активное
направление. При выборе направления подставляются:

- системная инструкция поведения модели (база + отраслевая специфика);
- перечень «Что я умею»;
- категории вопросов и терминология;
- примеры вопросов;
- температура генерации (`temperature`; пусто — общая `LLM_TEMPERATURE`);
- небольшой домысел (`allow_inference`).

Направления хранятся в таблице `domains`, редактируются в кабинете (создание,
изменение, дублирование, удаление, выбор активного), список выводится по алфавиту.
Встроенных направлений 20, у каждого до ~30 примеров вопросов. Активное
направление хранится в настройках (`domain_profile`), значение по умолчанию —
`DOMAIN_PROFILE`.

При смене направления ручные правки «Что я умею» сбрасываются — действует список
направления. Если список пуст, берётся перечень из БД админа, иначе из
`app/capabilities.py`. При пустой инструкции направления используется общий
`SYSTEM_PROMPT`. Каталог-образец — `app/domains.py` (`SEED`, `SEED_VERSION`).

```bash
# каталог и активное направление
curl -s -b cookie.txt localhost:8091/api/admin/domain | jq

# выбрать сферу деятельности
curl -s -b cookie.txt -X PATCH localhost:8091/api/admin/domain \
  -H 'Content-Type: application/json' -d '{"profile": "legal"}'

# создать/изменить/удалить/дублировать направление
curl -s -b cookie.txt -X POST localhost:8091/api/admin/domains \
  -H 'Content-Type: application/json' \
  -d '{"title":"Клиника","system_prompt":"Ты — ассистент клиники...","categories":["приёмы"]}'
curl -s -b cookie.txt -X PUT localhost:8091/api/admin/domains/klinika \
  -H 'Content-Type: application/json' -d '{"system_prompt":"Новый текст инструкции"}'
curl -s -b cookie.txt -X POST localhost:8091/api/admin/domains/klinika/duplicate
curl -s -b cookie.txt -X DELETE localhost:8091/api/admin/domains/klinika
```

## Что умеет ассистент

На вопросы «что ты умеешь», «чем ты можешь помочь» ассистент отвечает без
обращения к LLM — перечнем возможностей плюс примерами вопросов из БД промтов.
Тот же перечень показан карточкой «Что я умею» на главной странице чата; при
выбранном направлении перечень берётся из него.

Перечень вынесен в настройки: карточка «Что я умею — источник текста» с редактором
разделов и пунктов, кнопками «Сохранить перечень», «Добавить раздел», «Вернуть
значение из кода» и указанием источника (`код: app/capabilities.py` или
«кабинет администратора»).

## Оценки ответов и статистика

- Под каждым ответом в чате — 👍/👎 и комментарий. После отправки форма
  блокируется.
- Статистика в кабинете: всего запросов, лайков, дизлайков; запросы по
  пользователям; распределение по дням; частые вопросы с разбивкой по оценкам.
- Ответы из исправлений помечены значком «исправленный» со ссылкой на страницу.
- Вопросы с дизлайком доступны фильтром и сортировкой «по оценке».

Во вкладке **«Оценки и правки»** каждый вопрос свёрнут в строку с датой, автором,
временем ответа и числом источников; клик раскрывает ответ, оценку, комментарий и
кнопку «Исправить ответ». Список листается по 10 запросов. У запроса сохраняется
источник `origin`: `web`, `api` или `generated`; запросы не из web помечены как
«системный».

```bash
curl -s -b cookie.txt 'localhost:8091/api/admin/requests?username=user&limit=10&offset=0' | jq
curl -s -b cookie.txt 'localhost:8091/api/admin/requests?origin=api' | jq
curl -s -b cookie.txt localhost:8091/api/admin/stats | jq
```

## Исправления ответов

Админ может создать исправление по конкретному вопросу или отредактировать ответ
в списке запросов. Исправления хранятся в `app.db` (таблица `corrections`) и
индексируются в коллекции Qdrant `corrections`.

**При создании и редактировании обязательны документ и страницы.** Админ выбирает
документ из `data/docs` и указывает страницы (`12-15`, `7, 12-15`), затем кнопка
«Подставить текст страниц» извлекает текст этих страниц из PDF как основу.

Ссылка хранится в исправлении (`doc_name`, `doc_pages`, `doc_ref`) и показывается
пользователю: «Документация: FileAuditor_installation.pdf, с. 3». Без заполненных
полей API отвечает `400`.

Как исправления влияют на ответы:

1. При каждом вопросе ищется похожий вопрос среди активных исправлений.
2. Если косинусная схожесть ≥ `CORRECTION_MATCH_THRESHOLD` (по умолчанию `0.86`),
   сразу отдаётся исправленный ответ с пометкой и ссылкой; LLM не вызывается.
3. Иначе до `CORRECTION_EXAMPLES` похожих исправлений добавляются в промпт как
   примеры.
4. Статус `disabled` исключает исправление из подбора.
5. Ложные совпадения отсекаются по пересечению значимых слов
   (`CORRECTION_OVERLAP_WORDS`, по умолчанию 2) либо очень высокой схожести
   (≥ 0,95).

Правка из «Оценок и правок» не спрашивает ID: правило с тем же вопросом
обновляется, иначе создаётся новое (`POST /api/admin/corrections/by-question`).
После сохранения интерфейс предлагает перейти к исправлению и подсвечивает строку.

```bash
curl -s -b cookie.txt localhost:8091/api/admin/documents | jq
curl -s -b cookie.txt -X POST localhost:8091/api/admin/documents/pages \
  -H 'Content-Type: application/json' \
  -d '{"doc_name":"FileAuditor_installation.pdf","doc_pages":"12-15"}' | jq
curl -s -b cookie.txt -X POST localhost:8091/api/admin/corrections \
  -H 'Content-Type: application/json' \
  -d '{"question":"Как установить FileAuditor?","answer":"...",
       "doc_name":"FileAuditor_installation.pdf","doc_pages":"12-15"}'
```

## Сверка исправлений с документацией

Каждое активное исправление проверяется по документации: система извлекает текст
указанных страниц, добавляет близкие фрагменты из индекса и просит LLM вынести
вердикт `VERIFIED` или `REVIEW` с комментарием. Расхождение **не отключает**
исправление: оно помечается «требует проверки».

| Когда | Как |
|-------|-----|
| Автоматически | сразу после успешной фоновой индексации |
| Вручную | «Исправления» → «Проверить исправления по документации» |
| Сбросить | «Исправления» → «Сбросить результаты проверки» |

Результат хранится в исправлении (`check_status`, `check_comment`, `checked_at`,
`check_collection`) и показывается счётчиками «подтверждено / требует проверки».
Причины `REVIEW` без LLM: не указан документ или страницы, файл не найден, текст
страниц не извлёкся.

```bash
curl -s -b cookie.txt localhost:8091/api/admin/verify | jq
curl -s -b cookie.txt -X POST localhost:8091/api/admin/verify
curl -s -b cookie.txt -X POST localhost:8091/api/admin/verify/reset
```

## Словарь синонимов

Отдельная БД `data/synonyms/synonyms.db`, таблица `synonyms`:

| Поле | Назначение |
|------|------------|
| `term` | термин (первичный ключ, в нижнем регистре) |
| `synonyms` | синонимы через запятую |
| `author` | кто изменил |
| `updated_at` | время изменения |

Словарь расширяет поисковый запрос: вопрос разбивается на слова, для терминов
строятся варианты с подстановкой синонимов (учитываются падежные формы;
многословные термины ищутся как фразы). Варианты запрашиваются последовательно,
результаты объединяются по `(source, chunk)` и обрезаются до `RETRIEVE_TOP_K`.
Кэш — `SYNONYMS_CACHE_TTL` секунд.

При первом старте каталог наполняется стартовым набором (`app/synonyms.py`), дальше
его правит администратор. Активная сфера может переопределять отдельные термины
(домен-оверлей).

```bash
make synonyms               # текущий словарь
make synonyms-expand Q="как активировать лицензию"
make seed-synonyms          # пересоздать стартовый каталог
```

## Обучение ассистента

Отдельный чат для администратора (вкладка **«Обучение»**) — работа с моделью в
режиме наставника:

1. **Диалог.** Наставник отвечает по блокам «Ошибка», «Что изучить» и «Как
   ответить». Перед ответом он получает три фрагмента документации по теме с
   названиями, страницами и ссылками.
2. **Черновик урока.** Кнопка «Собрать черновик урока из диалога» превращает
   переписку в структуру: тема, типичный вопрос, эталонный ответ, ключевые
   моменты, документы. Черновик можно поправить перед сохранением.
3. **Урок в базе.** Уроки хранятся в `lessons`, индексируются в коллекции Qdrant
   `lessons` и подмешиваются в промпт всем пользователям на похожие вопросы.

Список уроков листается по 10, поиск по теме/вопросу сбрасывает страницу.

**Автообучение из исправлений.** Каждое сохранённое исправление сразу уходит
наставнику и превращается в урок. Если урок с таким же вопросом уже есть, он
обновляется. Процесс идёт в фоне, журнал — в таблице `training_log`. Отключается
настройкой `TRAINING_FROM_CORRECTIONS=0`.

Подбор уроков — по смыслу (тема + вопрос + фокус), порог `LESSONS_MIN_SCORE`
(по умолчанию `0.75`), в промпт попадает не больше `LESSONS_MAX` уроков.

```bash
curl -s -b cookie.txt -X POST localhost:8091/api/admin/train/chat \
  -H 'Content-Type: application/json' \
  -d '{"history":[],"question":"ассистент отвечает общими словами, как надо правильно?"}'
curl -s -b cookie.txt localhost:8091/api/admin/lessons | jq
curl -s -b cookie.txt localhost:8091/api/admin/training/log | jq
curl -s -b cookie.txt -X POST localhost:8091/api/admin/training/run
```

## Автообучение и память вопросов

Вкладка **«Автообучение»** превращает поток вопросов в материал для улучшения
ассистента:

1. **Эвристическая оценка.** Сразу после ответа запрос оценивается без модели:
   отказ при наличии фрагментов, ответ без источников, дизлайк, ответ из
   исправления. Результат пишется в `request_evals`, проблемы — в `answer_issues`.
2. **Темы вопросов.** Похожие вопросы группируются по эмбеддингам
   (`question_topics`, `topic_requests`): у темы хранится представитель, число
   вопросов и число проблемных.
3. **LLM-судья.** По заданию модель сверяет ответ с фрагментами и возвращает
   строгий JSON: `verdict`, `score`, `reason`, `suggested_answer`. Судья может
   работать через отдельный endpoint (`JUDGE_BASE_URL`, `JUDGE_MODEL`,
   `JUDGE_API_KEY`), получает few-shot примеры из `JUDGE_FEWSHOT_PATH`,
   проверяет ответ по схеме и повторяет запрос один раз, если JSON невалиден.
4. **Уроки-кандидаты.** Из проблемных тем (не меньше `AUTOLEARN_MIN_TOPIC_HITS`)
   наставник собирает уроки со статусом `candidate`. Они не попадают в ответы,
   пока администратор не одобрит их; одобренный урок становится `active`.

### Вердикты

| Вердикт | Значение | Источник |
|---------|----------|----------|
| `ok` | ответ верный и достаточный | эвристика / LLM |
| `partial` | неполный или расплывчатый | эвристика / LLM |
| `wrong` | противоречит фрагментам | эвристика (дизлайк) / LLM |
| `refused_wrongly` | отказ, хотя ответ в фрагментах есть | LLM |
| `refused` | отказ (ответа нет во фрагментах) | эвристика |
| `unknown` | вердикт не распознан | эвристика |

Эвристика обновляется при каждом ответе, но **не затирает вердикт модели**
(`method='llm'`). Ошибки (`downvote`, `refusal`, `no_sources`, `llm_wrong`) имеют
статус `open`, `resolved` или `dismissed`.

### Судья и калибровка

Судья возвращает только допустимые значения (`ok`, `partial`, `wrong`,
`refused_wrongly`) и `score` в диапазоне 0–1; при нарушении схемы выполняется
один повтор, после чего ставится `unknown`. Токены судьи учитываются в метрике
`llm_tokens_total{kind="judge",type="prompt"|"completion"|"total"}`.

Темы с оценкой судьи ниже `AUTOLEARN_MIN_JUDGE_SCORE` (по умолчанию `0.6`) не
порождают урок-кандидат. Согласие судьи с оценками пользователей видно в
карточке автообучения и в `GET /api/admin/autolearn/calibration`: сравниваются
вердикты `method='llm'` и голоса `up`/`down`.

### Память вопросов и схожесть

Сгенерированные вопросы сохраняются в таблице `generated_questions` вместе с
нормализованным текстом, источником, результатом прогона и вектором. Это даёт:

- **память** — повторно сгенерированные вопросы распознаются по нормализованному
  тексту и не создаются заново;
- **почти-дубли** — при схожести ≥ `QUESTIONGEN_DEDUP_THRESHOLD` вопрос помечается
  как дубликат (`duplicate_of`);
- **кластеры** — жадная центроидная кластеризация по эмбеддингам с порогом
  `QUESTIONGEN_SIM_THRESHOLD`; в карточке видно, сколько вопросов в кластере.

Карточка **«Память вопросов и схожесть»** показывает сохранённые вопросы, дубли и
кластеры; кнопка «Пересчитать схожесть» пересчитывает векторы и кластеры
(`QUESTIONGEN_SIM_LIMIT` ограничивает объём).

### Область анализа и параметры

Что попадает в анализ, задают `AUTOLEARN_WINDOW` (последние N запросов) и
`AUTOLEARN_DAYS` (последние N дней, `0` — без ограничения). «Быстрый анализ»
считает эвристики и темы, «Полный анализ с моделью» дополнительно прогоняет
LLM-судью и собирает уроки-кандидаты.

| Параметр | По умолчанию | Назначение |
|----------|--------------|------------|
| `AUTOLEARN_WINDOW` | `500` | сколько последних запросов оценивается |
| `AUTOLEARN_DAYS` | `30` | ограничить анализ днями, `0` — без ограничения |
| `AUTOLEARN_LLM_ENABLED` | `1` | звать ли LLM-судью |
| `AUTOLEARN_LLM_LIMIT` | `20` | сколько запросов за прогон отдавать судье |
| `AUTOLEARN_TOPIC_THRESHOLD` | `0.84` | порог схожести вопросов для темы |
| `AUTOLEARN_MIN_TOPIC_HITS` | `3` | проблемных вопросов для урока-кандидата |
| `AUTOLEARN_MIN_JUDGE_SCORE` | `0.6` | минимальная оценка судьи для урока-кандидата |
| `AUTOLEARN_MAX_TOPICS` | `300` | предохранитель по числу тем |
| `JUDGE_BASE_URL` | — | отдельный OpenAI-совместимый endpoint судьи |
| `JUDGE_API_KEY` | — | ключ судьи (пусто — ключ LLM) |
| `JUDGE_MODEL` | — | модель судьи (пусто — `LLM_MODEL`) |
| `JUDGE_FEWSHOT_PATH` | `/data/eval/judge_fewshot.json` | few-shot примеры судьи |
| `QUESTIONGEN_VARIANTS` | `3` | сколько переформулировок на фрагмент |
| `QUESTIONGEN_SIM_THRESHOLD` | `0.84` | порог схожести для кластера |
| `QUESTIONGEN_DEDUP_THRESHOLD` | `0.93` | порог почти-дубля |
| `QUESTIONGEN_SIM_LIMIT` | `2000` | максимум вопросов для анализа схожести |

## Генерация проверочных вопросов

Карточка **«Проверка на сгенерированных вопросах»** позволяет ассистенту самому
составить вопросы, ответить на них и оценить результат. Источники (`app/questiongen.py`):

- `docs` — по фрагментам проиндексированной документации;
- `topics` — по накопленным темам вопросов;
- `domain` — по активной сфере (примеры, категории, терминология).

Для каждого фрагмента генерируется несколько переформулировок (`QUESTIONGEN_VARIANTS`):
разные наклонения, формы и формулировки, чтобы проверить устойчивость поиска.
Вопросы проходят обычный ответ ассистента, пишутся в журнал с `origin='generated'`
и оцениваются. Фоновый прогон показывает стадии и число прогнанных вопросов; при
`QUESTIONGEN_JUDGE` подключается LLM-судья.

| Параметр | По умолчанию | Назначение |
|----------|--------------|------------|
| `QUESTIONGEN_COUNT` | `10` | сколько вопросов сгенерировать и прогнать |
| `QUESTIONGEN_SOURCES` | `docs,topics,domain` | источники вопросов |
| `QUESTIONGEN_JUDGE` | `1` | подключать LLM-судью |

```bash
curl -s -b cookie.txt localhost:8091/api/admin/questiongen | jq
curl -s -b cookie.txt -X POST localhost:8091/api/admin/questiongen/run \
  -H 'Content-Type: application/json' \
  -d '{"count": 20, "sources": ["docs", "domain"], "judge": true}'
curl -s -b cookie.txt 'localhost:8091/api/admin/questiongen/report?limit=20&offset=0' | jq
```

## Первичное обучение по сфере

Когда документы проиндексированы **и** выбрана сфера с примерами вопросов, система
автоматически запускает первичное обучение (`app/bootstrap.py`). Несколько циклов
«вопросы → ответы → эвристика → LLM-судья → темы → уроки-кандидаты»:

1. **Цикл 1** — примеры вопросов активного направления.
2. **Циклы 2..N** — новые вопросы по документации и накопленным темам.

Уроки остаются кандидатами до одобрения. Прогон идёт в фоне; карточка показывает
готовность, текущий цикл и таблицу результатов. Автозапуск срабатывает один раз
для пары «направление + индекс»; при смене сферы или новой загрузке документов
обучение стартует заново.

| Параметр | По умолчанию | Назначение |
|----------|--------------|------------|
| `BOOTSTRAP_CYCLES` | `3` | циклов обучения |
| `BOOTSTRAP_COUNT` | `30` | вопросов в цикле |
| `BOOTSTRAP_JUDGE` | `1` | LLM-судья и сбор уроков-кандидатов |

```bash
curl -s -b cookie.txt localhost:8091/api/admin/bootstrap | jq
curl -s -b cookie.txt -X POST localhost:8091/api/admin/bootstrap/run \
  -H 'Content-Type: application/json' -d '{"cycles": 3, "count": 30}'
```

## Документация из кабинета

Вкладка **«Документация»** показывает файлы из `data/docs` (включая `upload`) с
форматом, размером, числом фрагментов в индексе и датой изменения. Список
постраничный (20 на страницу), с поиском по имени. Отсюда можно:

- **загрузить файл с ПК** — `POST /api/admin/docs/upload` (`multipart/form-data`,
  поле `file`); поддерживаются все форматы из `loaders.SUPPORTED`, размер до
  `UPLOAD_MAX_MB`;
- **скачать по прямой http-ссылке** — `POST /api/admin/docs/url` с
  `{"url": "<DOCS_BASE_URL>MongoDB_update.pdf"}`; HTML-страницы не принимаются;
- **переиндексировать один документ** — `POST /api/admin/docs/{имя}/index`;
- **удалить документ** — `DELETE /api/admin/docs/{имя}`: файл удаляется с диска,
  точки — из индекса. Каталог `data/docs` смонтирован на запись, поэтому удаление
  физическое.

Загруженные и скачанные файлы сразу попадают в индекс: `ingest.index_single`
читает документ, режет на фрагменты и пишет их в активную коллекцию, предварительно
удаляя старые точки источника. Имя проверяется на совпадения: если такое имя уже
есть, новый файл сохраняется как `имя_2.pdf`.

**Поддерживаемые форматы:** PDF, DOCX/DOC, PPTX/PPT, XLSX/XLS, ODT/ODS/ODP,
EPUB, HTML, CSV/TSV, JSON, XML, YAML, Markdown, reStructuredText, LOG, SQL,
Shell/BAT/PowerShell и исходный код (Python, JS/TS, Java, Go, Rust, C/C++, C#,
Ruby, PHP, Perl, CSS, SVG, TeX, SRT/VTT).

```bash
curl -s -b cookie.txt 'localhost:8091/api/admin/docs?limit=20&offset=0' | jq
curl -s -b cookie.txt -F 'file=@manual.pdf' localhost:8091/api/admin/docs/upload | jq
curl -s -b cookie.txt -X POST localhost:8091/api/admin/docs/url \
  -H 'Content-Type: application/json' \
  -d '{"url":"<DOCS_BASE_URL>MongoDB_update.pdf"}' | jq
curl -s -b cookie.txt -X DELETE localhost:8091/api/admin/docs/MongoDB_update.pdf | jq
```

## Индексация сайтов

Помимо файлов ассистент умеет отвечать по информации на сайтах. Администратор
добавляет домены или отдельные адреса на вкладке **«Индексация»** (карточки
«Сайты для индексации» и «Обход сайтов») и нажимает «Обойти сайты».

1. Обход в ширину в пределах того же хоста; служебные страницы (`/login`, `/cart`,
   `/subscribe` и подобные) и не-HTML файлы пропускаются.
2. Учитывается `robots.txt` (`WEB_CRAWL_RESPECT_ROBOTS`), между запросами пауза
   `WEB_CRAWL_DELAY_MS`, таймаут `WEB_CRAWL_TIMEOUT`.
3. Из HTML вырезаются `script`, `style`, `nav`, `header`, `footer`, `aside`,
   `form`; добавляются заголовок, `meta description` и первый заголовок.
4. Текст режется тем же чанкером и пишется в активную коллекцию. Источник —
   `web/<host>/<path>`, в payload — `url` и `title`.
5. Перед новым обходом ранее проиндексированные страницы сайтов удаляются.
6. Веб-источники участвуют в ответах наравне с документацией.

| Параметр | По умолчанию | Смысл |
|----------|--------------|-------|
| `WEB_CRAWL_MAX_PAGES` | `2000` | максимум страниц с одного сайта |
| `WEB_CRAWL_DELAY_MS` | `500` | пауза между запросами |
| `WEB_CRAWL_TIMEOUT` | `20` | таймаут запроса, сек |
| `WEB_CRAWL_RESPECT_ROBOTS` | `1` | уважать `robots.txt` |
| `WEB_CRAWL_USER_AGENT` | DocsBot | идентификация обхода |

Для конкретного сайта можно задать свой лимит страниц в таблице.

```bash
curl -s -b cookie.txt localhost:8091/api/admin/sites | jq
curl -s -b cookie.txt -X PUT localhost:8091/api/admin/sites \
  -H 'Content-Type: application/json' \
  -d '{"sites":[{"url":"https://example.org","enabled":true,"max_pages":300}]}'
curl -s -b cookie.txt -X POST localhost:8091/api/admin/sites/start
```

## Фоновая переиндексация без простоя

Переиндексация **никогда не очищает рабочий индекс** и не блокирует поиск.

1. Чанки пишутся в новую коллекцию `docs_v<YYYYmmdd-HHMMSS>`; активный индекс
   `docs` не трогается.
2. Поиск идёт через алиас `docs` на старую коллекцию.
3. Когда все точки загружены, алиас переключается атомарно
   (`update_collection_aliases`).
4. После переключения удаляется предыдущая коллекция.

Если индексация упала до переключения, алиас остаётся на старой коллекции, поиск
продолжает работать, статус — `error` с текстом ошибки.

```bash
make reindex         # POST /reindex — запуск в фоне, ответ 202
make reindex-status  # GET /reindex  — статус и прогресс
```

| Поле | Значение |
|------|----------|
| `status` | `idle` / `running` / `paused` / `done` / `error` |
| `done`, `total` | загружено и всего чанков |
| `skipped_files` | файлы, загруженные ранее |
| `failed_files` | файлы с ошибкой чтения или загрузки |
| `collection` | версия новой коллекции |
| `started_at`, `finished_at`, `paused_at` | время старта, завершения, паузы |
| `error` | текст ошибки при `status = error` |
| `collection_info` | состояние коллекции под алиасом |

Повторный `POST /reindex` во время работы возвращает `202` и
`detail: переиндексация уже выполняется`.

## Срез прогресса, возобновление и пауза

Индексация продолжается после падения или перезапуска сервера.

**Состояние** — `data/index_state/index.db`:

| Таблица | Содержимое |
|---------|------------|
| `runs` | `collection`, `status`, `started_at`, `finished_at`, `error` |
| `file_progress` | `collection`, `source_key`, `size`, `mtime`, `chunks`, `done`, `updated_at` |

- каждые `INGEST_CHECKPOINT_EVERY` чанков делается срез;
- файлы с неизменившимися `size`/`mtime` пропускаются;
- дополнительно сверяется Qdrant: номера загруженных чанков читаются из payload;
- ID точек детерминированы (`uuid5(source:chunk)`), дозагрузка идемпотентна;
- незавершённая версия `docs_v<ts>` продолжается, а не создаётся заново.

```bash
make reindex-pause    # дописывает текущий батч и встаёт
make reindex-resume   # продолжает с последнего среза
make reindex          # на паузе тоже продолжает
```

## Ускорение индексации

| Параметр | Переменная | По умолчанию | Смысл |
|----------|------------|--------------|-------|
| Потоки индексации | `INGEST_WORKERS` | `8` | сколько файлов обрабатывается одновременно |
| Потоки CPU | `OMP_NUM_THREADS` | `12` | потоки torch при расчёте эмбеддингов |
| Размер батча эмбеддингов | `EMBED_BATCH` | `32` | сколько текстов кодируется за раз |
| Точек в одном upsert | `INGEST_BATCH_SIZE` | `64` | размер батча записи в Qdrant |

Практика: ~12 000 чанков на 16 ядрах — около 20 минут вместо ~2 часов при
`OMP_NUM_THREADS=4` и однопоточной индексации. Эмбеддинги считаются под
блокировкой, поэтому `INGEST_WORKERS` даёт прирост за счёт совмещения I/O,
чанкинга и записи с расчётом эмбеддингов.

## Резервное копирование и восстановление

`make backup` создаёт в `data/backups/<дата-время>/` согласованный набор:

- SQLite-копии `app.db`, `settings.db`, `synonyms.db`, `prompts.db`,
  `index_state.db` через `sqlite3.backup` (без блокировки работающего сервиса);
- snapshot активной коллекции Qdrant (через API, затем `docker compose cp`);
- `docs.tar.gz` с `data/docs` (исходники и загрузки);
- `system_password.txt` и `qdrant_collection.txt`;
- `manifest.json` с размерами файлов для проверки целостности.

```bash
make backup                 # создать копию, оставить последние 7
make backup-status          # размер, возраст и список копий
make restore BACKUP=data/backups/20261020-201738           # без документов
make restore BACKUP=data/backups/20261020-201738 DOCS=1    # с data/docs
```

Восстановление необратимо и требует `RESTORE=yes` (Makefile передаёт его сам):
скрипт проверяет манифест, останавливает `app`, возвращает SQLite и пароль
system, при `--docs` распаковывает документацию, восстанавливает коллекцию
Qdrant из snapshot, переключает алиас `docs`, запускает приложение и проверяет
`/health?deep=1`. `.env` и внешние секреты в копию не входят — храните их
отдельно.

Пример cron (ежедневно в 02:30):

```cron
30 2 * * * cd /opt/compose/LLM && make backup >> data/backups/cron.log 2>&1
```

Каждая копия содержит полный snapshot документов: при 500 МБ документации и
retention 7 планируйте около 3,5 ГБ. Статус доступен в кабинете и через
`GET /api/admin/backup/status`.

## Локальная генерация на CPU

```bash
make pull-llm LLM_MODEL=qwen2.5:3b-instruct
```

По умолчанию `qwen2.5:3b-instruct` (~2 ГБ RAM) — подходит для сервера с 5 ГБ
оперативной памяти. При 8+ ГБ можно взять `qwen2.5:7b-instruct` — качество по
русскоязычным мануалам выше, но генерация медленнее.

Модели семейства DeepSeek: `deepseek-r1:7b` (4.7 ГБ) работает на CPU, но на
реальном запросе даёт около 3 минут из-за длинных «размышлений»;
`deepseek-r1:1.5b` — в разы быстрее. Полноразмерные модели (671B) на CPU не
запускаются. Модель переключается в настройках без перезапуска.

Либо внешний OpenAI-совместимый API:

```bash
LLM_BASE_URL=https://api.openai.com/v1
LLM_API_KEY=sk-...
LLM_MODEL=gpt-4o-mini
```

**Выбор модели и дообучение.** На CPU LoRA/QLoRA для Qwen2.5:3B нецелесообразны:
обучение идёт часами, а выигрыш ниже, чем от качественного retrieval. Система
обучается без изменения весов: исправления, уроки, синонимы, сферы деятельности,
память вопросов и уроки-кандидаты. Для GPU-сервера можно взять 7B, для CPU
остаётся `qwen2.5:3b-instruct`.

## Гибридный поиск и reranker

Поиск двухканальный с переранжированием:

- **Dense** — `multilingual-e5-base` с префиксами `query: ` и `passage: `.
- **Sparse (BM25)** — `Qdrant/bm25` из `fastembed` (`SPARSE_MODEL`). При индексации
  в точку пишется пара векторов `{"dense": [...], "sparse": {...}}`.
- **Слияние RRF** — `rag._hybrid_points` делает `prefetch` из двух запросов и
  объединяет их через `FusionQuery(fusion=RRF)`.
- **Reranker** — `BAAI/bge-reranker-v2-m3` пересчитывает порядок кандидатов:
  `RERANKER_CANDIDATES` → `RERANKER_TOP_K` в промпт.
- Старые коллекции без sparse-индекса не ломают поиск: `vectorstore.supports_sparse`
  проверяет индекс, и запрос уходит только в dense-канал.
- Модели прогреваются в фоне при старте (`main.warm_search`).
- Параметры меняются в кабинете и действуют сразу; смена моделей/префиксов
  помечена «требует переиндексации».
- `HYBRID_FUSION`: `rrf` (по умолчанию) или `dense`.

Задержка на CPU: гибридный запрос ~5 с, rerank 10 кандидатов ~4 с.

| Параметр | По умолчанию | Смысл |
|----------|--------------|-------|
| `HYBRID_SPARSE` | `1` | включать BM25-канал |
| `HYBRID_CANDIDATES` | `12` | сколько кандидатов берёт каждый канал |
| `RERANKER_ENABLED` | `1` | переранжирование cross-encoder'ом |
| `RERANKER_MODEL` | `BAAI/bge-reranker-v2-m3` | модель reranker'а |
| `RERANKER_CANDIDATES` | `10` | сколько кандидатов оценивает reranker |
| `RERANKER_TOP_K` | `5` | сколько оставляет в промпт |
| `RERANKER_MAX_LENGTH` | `512` | максимум токенов на пару |
| `SPARSE_MODEL` | `Qdrant/bm25` | sparse-модель fastembed |

## Родительские фрагменты

Режим parent-child улучшает полноту ответа: поиск и reranker работают по
мелким дочерним чанкам (`CHUNK_SIZE`), а в промпт попадает объемлющий
родительский фрагмент.

```dotenv
PARENT_CHILD_ENABLED=0
PARENT_CHUNK_SIZE=1800
PARENT_CHUNK_OVERLAP=200
```

- при индексации в payload дочерней точки пишутся `parent_id`, `parent_text`,
  `parent_chunk` и `parent_page`;
- `rag.retrieve` при включённом флаге переранжирует пул кандидатов, затем
  дедуплицирует результаты по `parent_id` и подставляет `parent_text`;
- без переиндексации режим не даёт эффекта: старые точки не содержат
  родительских полей и остаются дочерними;
- параметры доступны в кабинете (раздел «Поиск») и помечены как требующие
  переиндексации;
- по умолчанию режим выключен, чтобы не менять поведение существующего индекса.

## Мониторинг и здоровье

- `GET /health` — быстрый liveness: статус, коллекция, модели, устройство.
- `GET /health?deep=1` — readiness: ping Qdrant, наличие коллекции под алиасом
  `docs`, доступность Ollama и нужной модели, тест записи в SQLite. Ответ
  содержит `status` (`ok`/`degraded`) и `checks` с длительностью проверок.
- `GET /metrics` — Prometheus. Кроме HTTP-метрик:
  `llm_retrieval_latency_seconds`, `llm_reindex_duration_seconds`,
  `llm_tokens_total{kind="chat"|"judge",type="prompt"|"completion"|"total"}`.
- При остановке контейнера приложение дожидается текущего батча
  переиндексации (до 20 с), сохраняет срез и помечает прогон `paused`
  (при остановке контейнера — `interrupted`);
  `stop_grace_period` в compose — 30 с. После старта `make reindex` продолжит
  с последнего среза.

## Оценка качества

Эталонные вопросы — в `data/eval/dataset.json`:

```json
{"items": [{"question": "Как восстановить доступ к VPN?", "answer": "обратиться в ИБ"}]}
```

```bash
make evaluate              # grounded_rate, context_recall, hit_rate, answer_correctness
make evaluate-ragas        # faithfulness, answer_relevancy, context_precision
make evaluate-regression   # сравнение с baseline, код 1 при регрессе
```

Отчёт пишется в `data/eval/report.json`, история прогонов — в
`data/eval/history/<дата-время>.json`. `answer_correctness` — оценка судьи
(0–1) по соответствию ответа фрагментам; она дополняет keyword-hit и recall.

Первый `make evaluate-regression` создаёт `data/eval/baseline.json` из текущего
отчёта. Дальше метрики сравниваются с baseline: падение больше чем на 5%
(и не меньше 0,01) считается регрессом и даёт код выхода 1, что удобно для CI.
Путь к baseline можно задать: `python eval/regression.py --baseline ...`.

Тот же прогон запускается из кабинета: «Настройки» → карточка «Оценка
качества»; история и график — на вкладке «Автообучение» (карточка «История
качества»); API: `GET /api/admin/eval`, `POST /api/admin/eval/start` с
`{"ragas": true}`, `GET /api/admin/eval/history?limit=20`.

## Супер-тест

Сквозная проверка сервиса: `health` → `deep=1` → `login` → `me` → статус
резервных копий → настройки и проверка согласованности → модели и RBAC → сферы и
RBAC → статус индексации → коллекция → `retrieve` (должен найти фрагменты) →
`ask` по нескольким вопросам → оценка → автообучение / генерация вопросов /
память вопросов и схожесть / первичное обучение → история качества и калибровка
судьи → постраничная документация → сверка исправлений. При `--all-models`
дополнительно проверяется ответ по каждой модели Ollama.

Тест учитывает роль: для `system` вкладки моделей и сфер должны отвечать `200`,
для `admin` — `403`.

```bash
make super-test
make super-test ARGS="--questions 5 --all-models"

# вручную, роль system
docker compose exec -T app python eval/super_test.py --user system --password "..."
```

Скрипт `app/eval/super_test.py` печатает шаги и пишет отчёт
`data/eval/super_test_<дата-время>.md`. Код выхода 0 — все шаги пройдены, 1 — были
ошибки.

## Тюнинг качества

| Параметр | Переменная | По умолчанию |
|----------|------------|--------------|
| Размер чанка | `CHUNK_SIZE` | 1000 |
| Перекрытие | `CHUNK_OVERLAP` | 150 |
| Родительский фрагмент | `PARENT_CHUNK_SIZE` | 1800 |
| Фрагментов в ответе | `RETRIEVE_TOP_K` | 5 |
| Модель эмбеддингов | `EMBEDDING_MODEL` | `intfloat/multilingual-e5-base` |
| Порог исправления | `CORRECTION_MATCH_THRESHOLD` | 0.86 |
| Примеров исправлений | `CORRECTION_EXAMPLES` | 2 |
| Вариантов по синонимам | `SYNONYMS_MAX_VARIANTS` | 6 |
| Температура | `LLM_TEMPERATURE` | 0.1 |

Для коротких FAQ уменьшите `CHUNK_SIZE` до 400–600 и `CHUNK_OVERLAP` до 80.
Для длинных регламентов увеличьте `RETRIEVE_TOP_K` до 8–10 и переходите на
`intfloat/multilingual-e5-large` (нужна переиндексация, `EMBED_DIM` должен
совпадать с размерностью модели).

Если исправления подставляются слишком часто или редко — подкрутите
`CORRECTION_MATCH_THRESHOLD` (0.8 — чаще, 0.9 — реже). Если качество от синонимов
не растёт, поставьте `SYNONYMS_MAX_VARIANTS=3`; эффект проверяется через
`make synonyms-expand Q="..."` и сравнение `POST /retrieve`.

## Частые проблемы

- `Индекс документации пуст` — не выполнялась индексация либо `data/docs` пуст.
  Проверьте `curl -s localhost:8091/collection`.
- `401 Требуется вход` — запрос без cookie сессии; сначала `POST /api/login`.
- `403 Недостаточно прав` — нет роли `admin` (или `system` для моделей и сфер).
- Вкладки «Модели» и «Сфера деятельности» не видны — они доступны только роли
  `system`; войдите системным пользователем.
- Вход не проходит после смены `ADMIN_PASSWORD` — переменные читаются только при
  пустой таблице пользователей. Сбросьте пароль через кабинет.
- Вкладка кабинета пустая или не работают кнопки — обновите страницу (Ctrl+F5).
  `/` и `/admin` отдаются с `Cache-Control: no-store`.
- `400 При редактировании ответа обязательны документ и номера страниц` —
  выберите документ и укажите страницы (например `12-15`).
- `404 Документ не найден` — файла нет в `data/docs` (включая `upload`).
- Исправление не срабатывает — схожесть ниже `CORRECTION_MATCH_THRESHOLD` или
  мало общих значимых слов; проверьте порог или отключите исправление.
- `status: error` в `/reindex` — активный индекс не тронут, смотрите `error`;
  после исправления запустите `make reindex` ещё раз.
- Поиск не находит документы после смены `EMBEDDING_MODEL`, `CHUNK_SIZE` или
  `PARENT_CHILD_ENABLED` — выполните `make reindex`.
- `health?deep=1` вернул `degraded` — смотрите `checks`: нет коллекции под
  алиасом `docs`, недоступен Qdrant/Ollama, не скачана `LLM_MODEL` или нет
  прав на запись в SQLite.
- `make backup` падает на snapshot Qdrant — проверьте `QDRANT_PORT`,
  `QDRANT_API_KEY` и свободное место; копия создаётся только целиком.
- `restore` отказывается работать — нужен `RESTORE=yes` и целый
  `manifest.json`; восстановление перезаписывает SQLite и коллекцию.
- Судья возвращает `unknown` — проверьте `JUDGE_MODEL`/`JUDGE_BASE_URL` и
  валидность `judge_fewshot.json`; невалидный JSON повторяется один раз.
- Долгий первый запуск — скачивается модель эмбеддингов (~1.1 ГБ) в `app/.cache`.
- OOM на 7B — используйте `qwen2.5:3b-instruct` или внешний API.
- Долгая индексация — увеличьте `INGEST_WORKERS` и `OMP_NUM_THREADS` под число
  ядер, поднимите `EMBED_BATCH`.
- Обход сайтов идёт долго — снизьте `WEB_CRAWL_MAX_PAGES`, поднимите
  `WEB_CRAWL_DELAY_MS`; повторный обход безопасен.
- Файл MS Office 2003 не читается — проверьте, что в окружении есть `catdoc`,
  `xls2csv` и `catppt` (в Docker-образе они установлены).
- После удаления или замены файлов в `data/docs` индекс не меняется сам — нужен
  `make reindex` или кнопка на вкладке «Индексация».

## Техническая оценка

- Архитектура: микросервисная (FastAPI + Qdrant + Ollama + SQLite), Docker Compose.
- Векторизация: `intfloat/multilingual-e5-base`; гибридный поиск dense + BM25;
  переранжирование cross-encoder.
- Чанкинг: `RecursiveCharacterTextSplitter` (flat chunks); parent-child не
  применяется.
- Хранение: SQLite (пользователи, настройки, журнал, направления, память
  вопросов), Qdrant (векторный индекс).
- Безопасность: cookie-сессии, роли `user/admin/system`, скрытый системный
  пользователь, PBKDF2-SHA256.
- Масштабируемость: асинхронная индексация, батчи эмбеддингов, параллельная
  обработка, переиндексация без простоя.

### Экспертное заключение

Это сильный, продуманный проект уровня senior-разработки с редкими для таких
систем фичами (верификация исправлений, автообучение с LLM-судьёй, память
вопросов с кластеризацией, супер-тест). Основные ограничения — не
архитектурные, а эксплуатационные: SQLite под нагрузкой, отсутствие rate
limiting, CPU-генерация. Для локального корпоративного контура система готова к
использованию; для внешнего или высоконагруженного — требуется доработка по
пунктам 1–3 и 7–9.
