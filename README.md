# RAG-ассистент по внутренней документации

Локальный RAG-пайплайн на CPU: индексация документации (PDF/DOCX/TXT/MD/HTML/CHM)
и веб-сайтов в Qdrant эмбеддингами `multilingual-e5-base`, поиск по векторам,
генерация ответа с цитированием источников, веб-чат с авторизацией и кабинет
администратора: пользователи, оценки ответов, исправления ответов со ссылкой на
страницы документации, словарь синонимов, изображения из PDF, статистика запросов
и управление индексацией.

## Как это работает

```
data/docs/*.pdf, *.chm ──► chm_extract.py ──► data/extracted/*.txt
                                        │
                                        ▼
                       loaders.py → chunking → multilingual-e5-base
                                        │
                                        ▼
                    Qdrant: docs_v<timestamp>  ──alias swap──►  alias "docs"
                                        │
   вопрос ──► исправления админа (Qdrant: corrections)  ─┐     │
           └► словарь синонимов (расширение запроса) ──┐  │
           └► уроки администратора (Qdrant: lessons) ────┐│  │
                                                        ▼▼ ▼
                                          retrieval + LLM + цитаты [doc:chunk]
                                             │                │        │
                              изображения (Qdrant: images) ┘        │
                                                                        ▼
                                    app.db: вопрос, ответ, ссылка на страницу,
                                            оценка и комментарий пользователя
```

0. **Источники.** Файлы берутся из двух каталогов — `data/docs` и `data/extracted`
   (`DOCS_DIR` и `EXTRACTED_DIR`). Пока в `data/extracted` лежат распакованные
   CHM, в индексе появляются страницы с именами вроде `ESConsole/__.txt`: у части
   страниц заголовок состоит из непечатных символов. Если каталог распакованных
   текстов не нужен, достаточно его убрать — и обязательно пересоздать контейнер
   (`docker compose up -d --force-recreate app`): иначе bind-mount продолжит
   показывать старые файлы.
1. **Загрузка.** `loaders.py` читает PDF (pypdf), DOCX, TXT, MD, HTML; из CHM
   предварительно распаковывается текст (`chm_extract.py`, 7z + BeautifulSoup).
   Для PDF документ читается постранично, поэтому каждый чанк помнит номер
   страницы, а заголовок берётся из метаданных или первых строк.
2. **Чанкинг.** `ingest.split_text` режет текст `RecursiveCharacterTextSplitter`
   с перекрытием (`CHUNK_SIZE` / `CHUNK_OVERLAP`); страницы чанкуются раздельно,
   чтобы не терялась привязка к странице.
3. **Эмбеддинги.** `vectorstore.embed_passages` кодирует чанки моделью
   `intfloat/multilingual-e5-base` на CPU (префикс `passage: `), запросы —
   с префиксом `query: `, векторы нормализованы, косинусная метрика.
4. **Хранилище.** Qdrant, коллекция версионированная `docs_v<YYYYmmdd-HHMMSS>`,
   имя `docs` — алиас, через который идёт весь поиск.
5. **Расширение запроса.** `synonymdb.expand` подставляет синонимы из отдельной БД
   `data/synonyms/synonyms.db`, варианты ищутся в Qdrant, результаты
   объединяются по `(source, chunk)` и обрезаются до `RETRIEVE_TOP_K`.
6. **Исправления.** Отдельная БД `app.db` (таблица `corrections`) и коллекция
   Qdrant `corrections` с эмбеддингами вопросов; при заданной похожести
   исправленный ответ отдаётся вместо сгенерированного — вместе со ссылкой
   на документ и страницу.
7. **Retrieval + генерация.** `rag.retrieve` берёт `RETRIEVE_TOP_K` фрагментов,
   `rag.ask` собирает промпт с цитатами и обращается к LLM (Ollama или внешний
   OpenAI-совместимый API). Флаг `grounded` показывает, не был ли ответ
   отказом («нет информации»).
8. **Сайты.** Страницы сайтов пишутся в ту же активную коллекцию с источником
   `web/<host>/<path>` и URL в payload.
9. **Журнал.** Каждый вопрос и ответ пишутся в `app.db` с пользователем,
    временем, источниками, ссылкой и оценкой.
10. **Метаданные источника.** В payload каждой точки лежат `page`, `title`,
    `kind` (`file` / `web`) и `url` — для документации это ссылка на оригинал
    вида `<DOCS_BASE_URL><файл>.pdf`, для сайтов — адрес страницы.
    Благодаря этому карточка источника в чате показывает название, страницу и
    кликабельный оригинал (см. «Подробнее об источниках»).

## Требования

- Docker + Docker Compose v2
- ~5 ГБ RAM для `qwen2.5:3b-instruct` + эмбеддинги, ~8 ГБ для 7B
- ~1 ГБ на диске под веса эмбеддингов (в т. ч. кэш `./app/.cache`), ~50 МБ под изображения
- от 8 CPU-ядер для комфортной индексации (параллелизм настраивается)
- для обхода сайтов — исходящий HTTPS и вежливый `User-Agent`

## Быстрый старт

```bash
cp .env.example .env

# задать администратора (создаётся при первом старте)
# ADMIN_USERNAME=admin
# ADMIN_PASSWORD=сильный-пароль
# APP_TITLE=База знаний

# 1. документация в data/docs (PDF/DOCX/TXT/MD/HTML/CHM)
# 2. поднять qdrant + ollama + api
make up

# 3a. первичная индексация из CLI
make ingest

# 3b. либо индексация в фоне, поиск продолжает работать
make reindex

# 4. открыть чат и войти
# http://localhost:8091/
```

При первом старте автоматически создаются четыре БД:

| БД | Путь | Что хранит |
|----|------|------------|
| состояние индексации | `data/index_state/index.db` | срезы прогресса и незавершённые запуски |
| пользователи и журнал | `data/app/app.db` | учётные записи, сессии, вопросы и ответы, оценки, исправления, настройки |
| синонимы | `data/synonyms/synonyms.db` | словарь синонимов |
| изображения | `data/images` | извлечённые из PDF иллюстрации |

Прогресс фоновой индексации: `make reindex-status` или `GET /reindex`.
Кабинет администратора: `http://localhost:8091/admin`.

## Пользователи и авторизация

- Логин/пароль, сессия хранится в HttpOnly cookie `sid` (срок 14 дней).
- Пароли — PBKDF2-SHA256, 200 000 итераций, индивидуальная соль.
- Роли: `user` (чат, оценки) и `admin` (кабинет администратора).
- Первый администратор создаётся при первом старте приложения из переменных
  `ADMIN_USERNAME` / `ADMIN_PASSWORD` — только если таблица пользователей пуста.
- Без входа недоступны `/chat`, `/ask`, `/api/rate/*` и все эндпоинты
  `/api/admin/*`.

```bash
curl -s -c cookie.txt -X POST localhost:8091/api/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"..."}'

curl -s -b cookie.txt localhost:8091/api/me
curl -s -b cookie.txt -X POST localhost:8091/api/logout
```

Таблицы в `data/app/app.db`:

| Таблица | Содержимое |
|---------|------------|
| `users` | `id`, `username`, `salt`, `password_hash`, `role`, `active`, `created_at` |
| `sessions` | `token`, `user_id`, `created_at`, `expires_at` |
| `requests` | `id`, `user_id`, `username`, `question`, `answer`, `grounded`, `corrected`, `doc_name`, `doc_pages`, `doc_ref`, `sources`, `latency_ms`, `created_at` |
| `ratings` | `request_id`, `vote` (`up`/`down`), `comment`, `created_at`, `updated_at` |
| `corrections` | `id`, `question`, `answer`, `doc_name`, `doc_pages`, `doc_ref`, `status`, `check_status`, `check_comment`, `checked_at`, `check_collection`, `author`, `created_at`, `updated_at` |
| `lessons` | `id`, `topic`, `question`, `answer`, `focus`, `author`, `status`, `uses`, `created_at`, `updated_at` |
| `training_log` | `id`, `source`, `correction_id`, `lesson_id`, `status`, `note`, `author`, `created_at` |
| `settings` | `key`, `value`, `updated_at` (название базы, перечень возможностей, параметры) |

## Кабинет администратора

`http://localhost:8091/admin` (только для роли `admin`). Вкладки:

| Вкладка | Возможности |
|---------|-------------|
| Обзор | сводка, запросы по пользователям, график по дням, топ вопросов, счётчики проверки исправлений |
| Пользователи | создание, смена пароля, роль, вкл/выкл, удаление |
| Оценки и правки | журнал запросов с фильтрами, поиском и сортировкой (дата, оценка, время ответа, пользователь; по возрастанию/убыванию), редактирование ответа с указанием документа и страниц |
| Исправления | исправления со ссылкой на страницы, результат сверки с документацией, вкл/выкл, удаление, запуск сверки |
| Синонимы | словарь: правка по месту, добавление, массовый импорт, проверка вариантов запроса |
| Обучение | чат с наставником, черновики уроков из диалога, список уроков, журнал автообучения из исправлений |
| Настройки | название базы знаний, параметры модели и пайплайна, перечень «Что я умею», извлечение изображений |
| Индексация | переиндексация документации (запуск, пауза, прогресс), список сайтов и обход с прогрессом, извлечение изображений из PDF |

При выдаче роли `admin` пользователю в чате появляется кнопка «Админ».

Связи между вкладками:

- правка ответа в «Оценках и правках» создаёт запись в общем списке
  «Исправления» — после сохранения предлагается переход с подсветкой строки, а у
  запроса с уже созданным исправлением показывается метка «открыть исправление #N»;
- каждое исправление автоматически становится уроком в «Обучении» (см. ниже);
- параметры из «Настроек» применяются мгновенно, кроме помеченных как
  «требует переиндексации» — для них нужна вкладка «Индексация»;
- карточки «Сайты для индексации», «Обход сайтов» и «Извлечение изображений»
  живут на вкладке «Индексация», их параметры — в группе «Настройки».

## Настройки

**Название базы знаний.** Хранится в таблице `settings`; значение по умолчанию
берётся из `APP_TITLE` в `.env`. Пока админ не менял название, используется
`APP_TITLE`; кнопка «Вернуть значение из .env» возвращает его. Заголовок в шапке
чата и `<title>` страницы обновляются сразу.

**Параметры модели и пайплайна.** Любой можно переопределить из кабинета:
значение попадает в таблицу `settings` и применяется сразу, кнопка «Сбросить»
возвращает значение из `.env`.

| Группа | Параметры |
|--------|-----------|
| Генерация | `LLM_MODEL` (выпадающий список моделей с LLM-сервера), `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_TEMPERATURE`, `LLM_MAX_TOKENS` |
| Поиск и чанкинг | `RETRIEVE_TOP_K`, `CORRECTION_MATCH_THRESHOLD`, `CORRECTION_EXAMPLES`, `SYNONYMS_MAX_VARIANTS`, `EMBEDDING_MODEL`¹, `CHUNK_SIZE`¹, `CHUNK_OVERLAP`¹ |
| Поведение ответа | `PROMPTS_MAX`, `SYSTEM_PROMPT` |
| Сайты и обход | `WEB_CRAWL_MAX_PAGES`, `WEB_CRAWL_TIMEOUT`, `WEB_CRAWL_DELAY_MS`, `WEB_CRAWL_RESPECT_ROBOTS`, `WEB_CRAWL_USER_AGENT` |
| Изображения | `IMAGE_SEARCH_ENABLED`, `IMAGE_MATCH_THRESHOLD`, `IMAGE_MAX`, `IMAGE_MIN_SIDE`, `IMAGE_PER_PAGE`, `IMAGE_PER_DOC`, `IMAGE_SKIP_FULLPAGE` |
| Индексация | `INGEST_WORKERS`, `INGEST_BATCH_SIZE`, `INGEST_CHECKPOINT_EVERY` |

¹ Помечены в интерфейсе как «требует переиндексации»: вступят в силу со следующей
индексацией, о чём сообщает ответ API в поле `requires_reindex`. Остальные
применяются немедленно. Типы проверяются на сервере: `int` и `float` должны быть
числами, непустой системный промпт обязателен, неизвестный ключ отклоняется.
Логические параметры — переключатели «Включено / Выключено».

Все параметры присутствуют в `.env` (с группировкой и комментариями) и
проброшены в контейнер: `docker-compose.yml` подключает `.env` через `env_file`,
поэтому многострочный `SYSTEM_PROMPT` тоже передаётся без обрезаний.

## Что умеет ассистент

На вопросы вида «что ты умеешь», «чем ты можешь помочь», «какие у тебя
возможности» ассистент отвечает без обращения к LLM — перечнем возможностей
плюс примерами вопросов из БД промтов, подобранными по составу индекса. Тот же
перечень показан карточкой «Что я умею» на главной странице чата и продублирован
в `SYSTEM_PROMPT`.

Перечень вынесен в настройки: на вкладке «Настройки» есть карточка «Что я умею —
источник текста» с редактором разделов и пунктов, кнопками «Сохранить перечень»,
«Добавить раздел», «Вернуть значение из кода» и прямой строкой **источник** —
`код: app/capabilities.py` или «кабинет администратора».

Содержание перечня по умолчанию:

- работа с текстом и информацией: ответы на вопросы, объяснение сложных тем,
  написание, редактирование, сокращение и перевод текстов, анализ документов,
  статей и договоров, помощь с письмами, резюме, отчётами и презентациями;
- база знаний компании: поиск по проиндексированной документации с
  показанием источников и ссылок;
- ограничения: ассистент не выходит в интернет, не выполняет действия в
  системах и не выдумывает факты.

## Оценки ответов и статистика

- Под каждым ответом в чате — 👍/👎 и поле комментария. После отправки форма
  блокируется: поле очищается и гасится, кнопка меняется на «Отправлено», оценка
  больше не меняется.
- Статистика в кабинете: всего запросов, лайков, дизлайков; сколько запросов
  приходится на каждого пользователя; распределение по дням; самые частые вопросы
  с разбивкой по оценкам.
- Ответы, пришедшие из исправлений администратора, помечены значком
  «исправленный» вместе со ссылкой на страницу документа.
- Вопросы с дизлайком доступны фильтром «Дизлайк» и сортировкой «по оценке».

Во вкладке **«Оценки и правки»**:

- каждый вопрос свёрнут в строку с датой, автором, временем ответа и числом
  источников; клик по вопросу раскрывает ответ, оценку, комментарий и кнопку
  «Исправить ответ»;
- список листается по 10 запросов на страницу («Назад»/«Вперёд»), счётчик «Всего»
  и переходы работают вместе с фильтрами;
- фильтр по пользователю строится по списку пользователей, плюс отдельный пункт
  «Системные (не из web)»;
- у каждого запроса сохраняется источник `origin`: `web` для чата, `api` для
  запросов к `/ask` и внешним API. Запросы не из web помечены в списке как
  «системный» вместо имени пользователя.

```bash
curl -s -b cookie.txt 'localhost:8091/api/admin/requests?username=user&limit=10&offset=0' | jq
curl -s -b cookie.txt 'localhost:8091/api/admin/requests?origin=api' | jq
```

```bash
curl -s -b cookie.txt localhost:8091/api/admin/stats | jq
curl -s -b cookie.txt 'localhost:8091/api/admin/requests?vote=down&sort=vote' | jq
```

## Исправления ответов

Админ может создать исправление по конкретному вопросу или отредактировать ответ
прямо в списке запросов. Исправления хранятся в `data/app/app.db` (таблица
`corrections`) и индексируются в отдельной коллекции Qdrant `corrections`
эмбеддингами вопросов.

**При создании и при любом редактировании ответа обязательны документ и номера
страниц.** Админ выбирает документ из списка файлов `data/docs` и указывает
страницы (`12-15`, `7, 12-15`), после чего кнопка «Подставить текст страниц»
извлекает текст этих страниц из PDF (pypdf) в поле ответа как основу — дальше
админ правит его вручную. Текстовые документы режутся на условные страницы по
символу разрыва страницы.

Ссылка хранится в исправлении (`doc_name`, `doc_pages`, `doc_ref`) и показывается
пользователю под ответом: «Документация: FileAuditor_installation.pdf, с. 3».
Без заполненных полей API отклоняет правку с `400`.

Как исправления влияют на ответы:

1. При каждом вопросе ищется похожий вопрос среди активных исправлений.
2. Если косинусная схожесть ≥ `CORRECTION_MATCH_THRESHOLD` (по умолчанию `0.86`),
   пользователю сразу отдаётся исправленный ответ с пометкой
   «Ответ скорректирован администратором» и ссылкой на страницу — генерация LLM
   не вызывается.
3. Иначе до `CORRECTION_EXAMPLES` похожих исправлений добавляются в промпт как
   примеры правильного ответа и стиля.
4. Статус `disabled` исключает исправление из подбора, `active` возвращает его.
5. Ложные совпадения отсекаются: кроме порога `CORRECTION_MATCH_THRESHOLD`
   проверяется пересечение значимых слов вопроса и исправления — не меньше
   `CORRECTION_OVERLAP_WORDS` (по умолчанию 2), либо очень высокая схожесть
   (≥ 0,95). Поэтому вопрос «Обновление сервера» больше не получает в ответ
   исправление про версии ОС, с которым у него всего одно общее слово.
   Оба порога меняются в кабинете.

Правка ответа из вкладки «Оценки и правки» не спрашивает ID: правило с тем же
вопросом обновляется автоматически, при отсутствии — создаётся новое
(`POST /api/admin/corrections/by-question`). Такое исправление сразу попадает в
общий список на вкладке «Исправления» — после сохранения интерфейс предлагает
кнопку «Показать в разделе “Исправления”» и подсвечивает нужную строку. Чтобы
видеть связь заранее, у запроса, по которому исправление уже есть, в журнале
показывается метка «открыть исправление #N».

```bash
curl -s -b cookie.txt localhost:8091/api/admin/documents | jq
curl -s -b cookie.txt -X POST localhost:8091/api/admin/documents/pages \
  -H 'Content-Type: application/json' \
  -d '{"doc_name":"FileAuditor_installation.pdf","doc_pages":"12-15"}' | jq
curl -s -b cookie.txt -X POST localhost:8091/api/admin/corrections \
  -H 'Content-Type: application/json' \
  -d '{"question":"Как установить FileAuditor?","answer":"...",
       "doc_name":"FileAuditor_installation.pdf","doc_pages":"12-15"}'
curl -s -b cookie.txt -X PATCH localhost:8091/api/admin/corrections/1 \
  -H 'Content-Type: application/json' -d '{"status":"disabled"}'
```

## Сверка исправлений с документацией

Каждое активное исправление проверяется по документации: система заново
извлекает текст указанных страниц, добавляет к нему близкие фрагменты из индекса
и просит LLM вынести вердикт `VERIFIED` (страницы подтверждают ответ) или `REVIEW`,
с коротким комментарием. Расхождение **не отключает** исправление: оно помечается
как «требует проверки», решение принимает администратор.

| Когда | Как |
|-------|-----|
| Автоматически | сразу после успешной фоновой индексации (`POST /reindex`) |
| Вручную | вкладка «Исправления» → «Проверить исправления по документации» |
| Сбросить результаты | вкладка «Исправления» → «Сбросить результаты проверки» |

Результат хранится в исправлении (`check_status`, `check_comment`, `checked_at`,
`check_collection` — коллекция, на которой проверяли), показывается в таблице
исправлений и в обзоре счётчиками «подтверждено / требует проверки».

Технические причины `REVIEW` без обращения к LLM: не указан документ или страницы,
файл не найден в `data/docs`, текст страниц не извлёкся или почти пуст — обычно
это ошибка в номерах страниц.

```bash
curl -s -b cookie.txt localhost:8091/api/admin/verify | jq
curl -s -b cookie.txt -X POST localhost:8091/api/admin/verify
curl -s -b cookie.txt -X POST localhost:8091/api/admin/verify/reset
```

## Словарь синонимов

Отдельная БД `data/synonyms/synonyms.db` (в контейнере
`/data/synonyms/synonyms.db`), таблица `synonyms`:

| Поле | Назначение |
|------|------------|
| `term` | термин (первичный ключ, в нижнем регистре) |
| `synonyms` | синонимы через запятую |
| `author` | кто изменил |
| `updated_at` | время изменения |

Словарь используется для расширения поискового запроса: перед обращением к Qdrant
вопрос разбивается на слова, для найденных терминов строятся варианты с
подстановкой синонимов (учёт падежных форм: «лицензию» → термин «лицензия»;
многословные термины вроде «рабочее время» ищутся как фразы). Варианты запрашиваются
последовательно, результаты объединяются по `(source, chunk)` с выбором лучшего
скора и обрезаются до `RETRIEVE_TOP_K`. Варианты, в которых смысл уже покрыт
(синоним присутствует в вопросе), отбрасываются. Кэш словаря —
`SYNONYMS_CACHE_TTL` секунд, сбрасывается при изменении через API.

При первом старте каталог наполняется стартовым набором по терминологии
продуктов (`app/synonyms.py`), дальше его правит администратор на вкладке
«Синонимы»: правка по месту, добавление термина, массовый импорт по строкам
`слово — синоним1, синоним2` и проверка, какие варианты запроса получатся для
произвольного вопроса.

```bash
make synonyms               # текущий словарь
make synonyms-expand Q="как активировать лицензию"
make seed-synonyms          # пересоздать стартовый каталог
```

## Обучение ассистента

Отдельный чат для администратора (вкладка **«Обучение»**) — работа с моделью в
режиме наставника. Админ приносит вопрос пользователя и ответ ассистента, который
его не устроил, и разбирает, как правильно:

1. **Диалог.** Наставник отвечает по трём блокам: «Ошибка», «Что изучить» и
   «Как ответить». Перед ответом он получает три фрагмента документации по теме
   вопроса (`lessons.documentation_context`) с названиями документов, страницами и
   ссылками — поэтому может сверяться с документацией и спорить, какой документ
   нужно изучить. Если администратор уже дал полный правильный ответ, наставник
   принимает его как эталон и не требует дополнительных данных; отказ «данных
   недостаточно» допустим только когда в сообщении нет ни вопроса, ни ответа.
2. **Черновик урока.** Кнопка «Собрать черновик урока из диалога» превращает
   переписку в структуру: тема, типичный вопрос пользователя, эталонный ответ,
   ключевые моменты и документы. Если админ дал полный ответ, эталонным считается
   именно он; пустые поля из-за нехватки данных не возвращаются — недостающие
   детали попадают в `focus`. Черновик показывается в форме — можно поправить
   перед сохранением.
3. **Урок в базе.** Уроки хранятся в таблице `lessons` БД `data/app/app.db`,
   индексируются в отдельной коллекции Qdrant `lessons` и **подмешиваются в
   промпт всем пользователям** на похожие вопросы: в начало промпта добавляется
   блок «Уроки администратора» с правильным ответом и списком моментов.

Список уроков справа сворачивается: клик по теме раскрывает или сворачивает урок,
состояние сохраняется при перерисовке и поиске. Уроки показываются по 10 на
страницу с кнопками «Назад»/«Вперёд»; поиск по теме или вопросу сбрасывает на
первую страницу.

**Автообучение из исправлений.** Каждое сохранённое исправление ответа
(создание, правка или авто-обновление по вопросу) сразу уходит наставнику:
наставник получает вопрос, исправленный ответ и ссылку на страницу, и превращает
это в урок — тема, типичный вопрос, эталонный ответ, ключевые моменты. Урок
попадает в промпт ко всем пользователям вместе с самим исправлением. Если урок с
таким же вопросом уже есть, он обновляется, а не дублируется.

Процесс идёт в фоне, а результат виден в карточке «Автообучение из исправлений»
на вкладке «Обучение»: источник, вопрос, ссылка, созданная тема урока, статус и
время. Кнопка «Обучить по всем активным исправлениям» отправляет в обучение всю
историю разом. Отключается настройкой `TRAINING_FROM_CORRECTIONS=0`. Журнал хранится
в таблице `training_log`.

Тема урока кодируется вместе с его вопросом и фокусом, поэтому подбор идёт по
смыслу вопроса, а не по точному совпадению слов. Порог отсечения —
`LESSONS_MIN_SCORE` (по умолчанию `0.75`), в промпт попадает не больше
`LESSONS_MAX` уроков. У каждого урока видно, сколько раз он сработал, есть
кнопки «Выключить» и «Удалить». Кнопка «Собрать черновик» не создаёт дубликаты:
индекс синхронизируется на каждом изменении и при старте приложения.

Настройки группы «Обучение»: `LESSONS_MAX`, `LESSONS_MIN_SCORE`,
`LESSONS_COLLECTION`.

```bash
curl -s -b cookie.txt -X POST localhost:8091/api/admin/train/chat \
  -H 'Content-Type: application/json' \
  -d '{"history":[],"question":"ассистент отвечает общими словами, как надо правильно?"}'
curl -s -b cookie.txt localhost:8091/api/admin/lessons | jq
curl -s -b cookie.txt -X POST localhost:8091/api/admin/lessons \
  -H 'Content-Type: application/json' \
  -d '{"topic":"Настройка перехвата почты","question":"Как настроить перехват почты?",
       "answer":"Создать БД перехвата, включить протоколы SMTP/POP3/IMAP…",
       "focus":"Модуль MailController; вкладка «БД и протоколы»"}'
curl -s -b cookie.txt "localhost:8091/api/admin/lessons/check?q=как+настроить+перехват+почты" | jq
curl -s -b cookie.txt localhost:8091/api/admin/training/log | jq
curl -s -b cookie.txt -X POST localhost:8091/api/admin/training/run
```

## Windows и Linux в ответах

Часть документации описана отдельно для разных ОС: один и тот же документ имеет
пару «общий / _linux», «_windows / _linux», а иногда имя отличается порядком слов
(`installation_SIEM.pdf` и `SIEM_installation_on_Linux.pdf`). Модуль `platforms.py`
определяет платформу
документа по имени файла и находит парный документ, сравнивая имена без маркера
ОС (`platforms.counterpart`).

Как это работает в ответе:

- **ОС названа в вопросе** («установка на Linux») — докачиваются только фрагменты
  этой платформы, вторая ОС не упоминается.
- **ОС не названа** — к найденным фрагментам докачивается до `PLATFORM_EXTRA_CHUNKS`
  фрагментов из парного документа (всего не больше `PLATFORM_MAX_EXTRA`), во
  фрагменты добавляется строка «Платформа», и в промпт уходит явное указание:
  вести ответ параллельно блоками «Для Windows» и «Для Linux» и перечислить
  различия. Правило продублировано в `SYSTEM_PROMPT`.
- В блоке «Документация, из которой взят ответ» платформенные документы
  помечены: `FileAuditor Installation Linux (FileAuditor_installation_linux.pdf), Linux, с. 4`.
- Если для одной из платформ в фрагментах ничего нет, ассистент прямо пишет, что
  в документации есть только вариант для другой ОС, и предлагает уточнить ОС.

Отключается целиком настройкой `PLATFORM_AWARE=0`.

Пока модель думает, поток чата не молчит: раз в `SSE_HEARTBEAT` секунд в SSE
отправляется служебная пустая строка `: ping`, чтобы соединение не рвётся на
долгой паузе перед первым токеном. Если обслуживающий LLM Ollama, в `docker-compose.yml`
заданы `OLLAMA_NUM_PARALLEL=2` (два одновременных запроса вместо очереди),
`OLLAMA_MAX_LOADED_MODELS=1` и `OLLAMA_KEEP_ALIVE=-1m` (модель не выгружается
из памяти между вопросами).

## Изображения из документации

Встроенные иллюстрации из PDF (схемы, скриншоты интерфейсов, рисунки из
руководств) извлекаются и индексируются отдельно от текста:

1. Вкладка «Индексация» → «Извлечь изображения из PDF» (фоновая задача с прогрессом).
2. `PyMuPDF` читает крупные встроенные картинки; мелкие тайлы, полностраничные
   фоны и повторы по содержимому отбрасываются, а оставшиеся распределяются по
   всему документу равномерно.
3. Файлы сохраняются в `data/images`, их подпись (текст страницы) кодируется той
   же моделью эмбеддингов и попадает в коллекцию Qdrant `images`.
4. После каждого ответа ассистент ищет картинки по вопросу и прикладывает те, у
   которых релевантность выше `IMAGE_MATCH_THRESHOLD` — не больше `IMAGE_MAX`.
   В чате они показываются с подписью (документ, страница) и открываются в полный
   размер по клику.
5. Показ переключается самим пользователем: под полем ввода в чате есть флажок
   «Изображения из документации». Состояние хранится в localStorage браузера и
   передаётся в `/chat` полем `show_images` — картинки не ищутся вовсе, когда
   флажок снят. Глобальное отключение для всех — `IMAGE_SEARCH_ENABLED=0`
   в настройках кабинета.

Тонкости отбора: `IMAGE_MIN_SIDE` (минимальная сторона, px), `IMAGE_PER_PAGE`,
`IMAGE_PER_DOC`, `IMAGE_SKIP_FULLPAGE` (доля площади страницы, выше которой картинка
считается фоном). Кнопка «Сохранить параметры и переизвлечь» применяет настройки и
запускает извлечение заново.

```bash
curl -s -b cookie.txt localhost:8091/api/admin/images | jq
curl -s -b cookie.txt -X POST localhost:8091/api/admin/images/start
```

## Документация из кабинета

Вкладка **«Документация»** показывает все файлы из `data/docs`, `data/extracted` и
`data/uploads` с форматом, размером, числом фрагментов в индексе и датой
изменения. Отсюда можно:

- **загрузить файл с ПК** — `POST /api/admin/docs/upload` (`multipart/form-data`,
  поле `file`), поддерживаются `.pdf`, `.docx`, `.txt`, `.md` и файлы до
  `UPLOAD_MAX_MB`;
- **скачать документ по прямой http-ссылке** — `POST /api/admin/docs/url` с
  `{"url": "<DOCS_BASE_URL>MongoDB_update.pdf"}`. HTML-страницы не
  принимаются: нужна прямая ссылка на файл;
- **переиндексировать один документ** — `POST /api/admin/docs/{имя}/index`;
- **удалить загруженный документ** — `DELETE /api/admin/docs/{имя}`: файл
  удаляется из `data/uploads`, а его точки — из активной коллекции Qdrant.
  Файлы из `data/docs` и `data/extracted` удалить нельзя, только переиндексировать.

Загруженные и скачанные файлы сразу попадают в индекс: `ingest.index_single`
читает документ, режет на фрагменты и пишет их в активную коллекцию, предварительно
удаляя старые точки этого источника, поэтому полная переиндексация не нужна.
Имя файла проверяется на совпадения: если такое имя уже есть в другом корне
документации, новый файл сохраняется как `имя_2.pdf` — иначе два файла делили бы
одни и те же точки индекса.

```bash
curl -s -b cookie.txt localhost:8091/api/admin/docs | jq
curl -s -b cookie.txt -F 'file=@manual.pdf' localhost:8091/api/admin/docs/upload | jq
curl -s -b cookie.txt -X POST localhost:8091/api/admin/docs/url \
  -H 'Content-Type: application/json' \
  -d '{"url":"<DOCS_BASE_URL>MongoDB_update.pdf"}' | jq
curl -s -b cookie.txt -X DELETE localhost:8091/api/admin/docs/MongoDB_update.pdf | jq
```

## Индексация сайтов

Помимо файлов документации ассистент умеет отвечать по информации на сайтах.
Администратор добавляет домены или отдельные адреса на вкладке **«Индексация»**
(карточки «Сайты для индексации» и «Обход сайтов») и нажимает «Обойти сайты».

1. Из стартового адреса обходятся ссылки в ширину, только в пределах того же
   хоста; служебные страницы (`/login`, `/reg/`, `/cart`, `/subscribe` и подобные)
   и не-HTML файлы пропускаются.
2. Учитывается `robots.txt` сайта (`WEB_CRAWL_RESPECT_ROBOTS`), между запросами
   пауза `WEB_CRAWL_DELAY_MS`, таймаут `WEB_CRAWL_TIMEOUT`.
3. Из HTML вырезаются `script`, `style`, `nav`, `header`, `footer`, `aside`, `form`,
   в текст добавляются заголовок страницы, `meta description` и первый заголовок.
4. Текст режется тем же чанкером, кодируется и пишется в **активную коллекцию**
   документации: переиндексация файлов не сбрасывается. Источник имеет вид
   `web/<host>/<path>`, в payload кладутся `url` и `title`.
5. Перед новым обходом ранее проиндексированные страницы сайтов удаляются, поэтому
   дубли не накапливаются.
6. Веб-источники участвуют в ответах наравне с документацией, а в чате их URL
   показывается кликабельной ссылкой.

| Параметр | По умолчанию | Смысл |
|----------|--------------|-------|
| `WEB_CRAWL_MAX_PAGES` | `2000` | предохранитель: максимум страниц с одного сайта |
| `WEB_CRAWL_DELAY_MS` | `500` | пауза между запросами |
| `WEB_CRAWL_TIMEOUT` | `20` | таймаут запроса, сек |
| `WEB_CRAWL_RESPECT_ROBOTS` | `1` | уважать `robots.txt` |
| `WEB_CRAWL_USER_AGENT` | бот DocsBot | идентификация обхода |

Для конкретного сайта можно задать свой лимит страниц прямо в таблице (пусто —
общий лимит).

```bash
curl -s -b cookie.txt localhost:8091/api/admin/sites | jq
curl -s -b cookie.txt -X PUT localhost:8091/api/admin/sites \
  -H 'Content-Type: application/json' \
  -d '{"sites":[{"url":"https://example.org","enabled":true,"max_pages":300}]'
curl -s -b cookie.txt -X POST localhost:8091/api/admin/sites/start
```

## Фоновая переиндексация без простоя

Ключевая особенность системы: переиндексация **никогда не очищает рабочий
индекс** и не блокирует поиск.

1. Чанки пишутся в **новую** коллекцию `docs_v<YYYYmmdd-HHMMSS>` — активный
   индекс `docs` в этот момент не трогается.
2. Поиск (`/retrieve`, `/ask`, `/chat`) идёт через алиас `docs` на старую
   коллекцию и отвечает как обычно.
3. Когда все точки загружены, алиас `docs` переключается на новую коллекцию
   (атомарно, `update_collection_aliases`).
4. Только после переключения удаляется предыдущая коллекция.

Если индексация упала на любом шаге до переключения — алиас остаётся на старой
коллекции, поиск продолжает работать, в статусе будет `error` с текстом ошибки.

```bash
make reindex         # POST /reindex — запуск в фоне, ответ сразу (202)
make reindex-status  # GET /reindex  — статус и прогресс
```

```json
  "total": 6138,
  "skipped_files": 3,
  "collection": "docs_v20240514-101203",
  "target": "docs",
  "collection_info": {"exists": true, "points": 6138, "status": "green"}
}
```

| Поле | Значение |
|------|----------|
| `status` | `idle` / `running` / `paused` / `done` / `error` |
| `done`, `total` | загружено и всего чанков |
| `skipped_files` | файлов, полностью загруженных ранее |
| `failed_files` | список файлов с ошибкой чтения или загрузки |
| `collection` | версия новой коллекции |
| `started_at`, `finished_at`, `paused_at` | время старта, завершения, паузы |
| `error` | текст ошибки, если `status = error` |
| `collection_info` | состояние коллекции, на которую сейчас ссылается алиас |

Повторный `POST /reindex`, пока идёт работа, возвращает `202` и
`detail: переиндексация уже выполняется` — параллельных задач не будет.

Те же операции доступны администратору на вкладке «Индексация».

## Срез прогресса, возобновление и пауза

Индексация не начинается заново после падения или перезапуска сервера.

**Состояние** хранится в отдельной БД `data/index_state/index.db` (SQLite):

| Таблица | Содержимое |
|---------|------------|
| `runs` | `collection`, `status` (`running`/`paused`/`interrupted`/`done`/`error`), `started_at`, `finished_at`, `error` |
| `file_progress` | `collection`, `source_key`, `size`, `mtime`, `chunks`, `done`, `updated_at` |

Механика:

- каждые `INGEST_CHECKPOINT_EVERY` чанков делается **срез** — в БД пишется, сколько
  чанков текущего файла уже загружено;
- при следующем запуске файлы с не изменившимися `size`/`mtime` пропускаются,
  изменённые переиндексируются полностью;
- дополнительно сверяется сам Qdrant: номера уже загруженных чанков читаются
  из payload, поэтому даже без БД индексация продолжит с места обрыва;
- ID точек детерминированы (`uuid5(source:chunk)`), поэтому дозагрузка
  идемпотентна — дубликатов не появляется;
- если запись о прогрессе потеряна, но осталась незавершённая версия коллекции
  `docs_v<ts>`, индексация продолжит её, а не создаст новую.

**Пауза**:

```bash
make reindex-pause    # POST /reindex/pause — дописывает текущий батч и встаёт
make reindex-resume   # POST /reindex/resume — продолжает с последнего среза
make reindex          # если индексация на паузе, тоже продолжает её
```

Значения `status`: `idle`, `running`, `paused`, `done`, `error`.

## Ускорение индексации

Индексация идёт в несколько потоков:

| Параметр | Переменная | По умолчанию | Смысл |
|----------|------------|--------------|-------|
| Потоки индексации | `INGEST_WORKERS` | `8` | сколько файлов обрабатывается одновременно |
| Потоки CPU | `OMP_NUM_THREADS` | `12` | потоки torch при расчёте эмбеддингов |
| Размер батча эмбеддингов | `EMBED_BATCH` | `32` | сколько текстов кодируется за раз |
| Точек в одном upsert | `INGEST_BATCH_SIZE` | `64` | размер батча записи в Qdrant |

Практика: 12 350 чанков на 16 ядрах — около 20 минут вместо ~2 часов при
`OMP_NUM_THREADS=4` и однопоточной индексации. Эмбеддинги считаются под
блокировкой, поэтому `INGEST_WORKERS` даёт прирост за счёт совмещения I/O,
чанкинга и записи с расчётом эмбеддингов.

## Стартовые промты

Стартовые вопросы хранятся в **отдельной БД** — SQLite `data/prompts/prompts.db`.

| Поле | Назначение |
|------|------------|
| `id` | порядок выдачи |
| `text` | текст промта (уникальный) |
| `product` | продукт (КИБ, Файловый аудитор, SIEM, ProfileCenter…) |
| `keywords` | ключевые слова для сопоставления с документами индекса |
| `source_url` | ссылка на источник (документ по `DOCS_BASE_URL` или раздел сайта) |
| `active` | показывается ли промт в чате |
| `created_at` | дата добавления |

Каталог наполнен по результатам анализа сайта, адрес которого задаётся в `.env` (`SITE_URL`)
(разделы «Продукты», «Решения», «Бизнес-задачи», «Контроль сотрудников») и
привязан к документации по адресу `DOCS_BASE_URL`, которая лежит в индексе.

Выдача динамическая: `GET /prompts` сначала выбирает промты, чьи `keywords`
встречаются среди реально проиндексированных документов, затем добавляет
универсальные продуктовые вопросы с сайта, и отдаёт первые `PROMPTS_MAX`.
Результат кэшируется на `PROMPTS_CACHE_TTL` секунд.

```bash
make prompts         # показать промты из БД
make prompts        # посмотреть текущую выдачу
```

При пустой БД каталог создаётся автоматически при старте приложения
(`PROMPTS_SEED_ON_START=1`).

Под каждым ответом раскрывается блок **«Источники (N) · подробнее»**. Для каждого
найденного фрагмента показывается:

| Элемент | Откуда берётся |
|---------|----------------|
| Название документа | `title` из метаданных PDF; если их нет — имя файла без расширения |

## Веб-интерфейс

`http://<host>:8091/` — вход, чат с потоковой генерацией (SSE), история диалога,
карточка «Что я умею», динамические стартовые промты, закреплённые сверху шапка и
снизу поле ввода с флажком изображений, раскрываемые источники под каждым ответом
(клик по фрагменту разворачивает его полностью; для веб-источников вместо
технической цитаты показывается кликабельная ссылка), оценки 👍/👎 с комментарием
и ссылка на страницу документа, если ответ пришёл из исправления администратора.

Каждый ответ из документации заканчивается блоком **«Документация, из которой
взят ответ»**: полные названия документов (`siem_help.pdf` → «SIEM Help»), номера
страниц и ссылки, а затем рекомендация детально ознакомиться с этими документами.
Блок формируется кодом (`rag.sources_block`, `rag.reference_block`), поэтому он
всегда есть и не зависит от того, как ответила модель; дополнительно модель
просят называть название документа прямо в тексте ответа (`SYSTEM_PROMPT`), а в
промпт передаётся `Документ: <название>` для каждого фрагмента.

## Локальная генерация на CPU

```bash
make pull-llm LLM_MODEL=qwen2.5:3b-instruct
```

По умолчанию `qwen2.5:3b-instruct` (~2 ГБ RAM) — подходит для сервера с 5 ГБ
оперативной памяти. При 8+ ГБ можно взять `qwen2.5:7b-instruct`
(`make pull-llm LLM_MODEL=qwen2.5:7b-instruct`) — качество ответов по
русскоязычным мануалам выше, но скорость генерации падает.

Модели семейства DeepSeek: `deepseek-r1:7b` (4.7 ГБ) работает на CPU, но на
реальном запросе из документации даёт около 3 минут (модель генерирует длинные
«размышления»); `deepseek-r1:1.5b` — в разы быстрее. Полноразмерные модели
(DeepSeek-V3/R1, 671B) на CPU не запускаются. Модель переключается в настройках
(`LLM_MODEL`) без перезапуска.

Либо внешний API (OpenAI-совместимый):

```bash
LLM_BASE_URL=https://api.openai.com/v1
LLM_API_KEY=sk-...
LLM_MODEL=gpt-4o-mini
```

## Гибридный поиск и reranker

Поиск сделан двухканальным и переранжировывается моделью:

- **Dense-канал** — как раньше: `multilingual-e5-base` с обязательными префиксами
  `query: ` для запроса и `passage: ` для фрагмента (`E5_QUERY_PREFIX`,
  `E5_PASSAGE_PREFIX` в `app/vectorstore.py`).
- **Sparse-канал (BM25)** — модель `Qdrant/bm25` из `fastembed`
  (`SPARSE_MODEL`). При индексации в каждую точку пишется пара векторов
  `{"dense": [...], "sparse": {...}}`, поэтому коллекция создаётся с именованным
  dense-вектором и sparse-индексом (`vectorstore.ensure_collection`).
- **Слияние RRF** — `rag._hybrid_points` делает `prefetch` из двух запросов
  (dense и sparse) и объединяет их через `FusionQuery(fusion=RRF)`. Веса
  подбирать не нужно, метод устойчив к разным шкалам расстояний.
- **Reranker** — `BAAI/bge-reranker-v2-m3` (cross-encoder) пересчитывает порядок
  кандидатов перед формированием ответа: `RERANKER_CANDIDATES` кандидатов →
  `RERANKER_TOP_K` в промпт (`rag.rerank`).
- Старые коллекции без sparse-индекса не ломают поиск: `vectorstore.supports_sparse`
  проверяет индекс, и тогда запрос уходит только в dense-канал. Полная
  переиндексация (`make reindex` или кнопка «Индексация») после первого
  внедрения занимает около часа и не мешает ответам: новая коллекция собирается
  отдельно, алиас `docs` переключается в конце.
- Модели прогреваются в фоне при старте (`main.warm_search`), поэтому первый
  вопрос не ждёт загрузки reranker.
- Все параметры retrieval'а меняются в кабинете (вкладка «Настройки», группы
  «Поиск и чанкинг», «Гибридный поиск», «Переранжирование»): код читает их через
  `settings.value(...)`, поэтому переключение `RERANKER_ENABLED`, `HYBRID_SPARSE`
  или `HYBRID_FUSION` действует сразу. При смене `RERANKER_MODEL`,
  `SPARSE_MODEL`, `E5_*_PREFIX` или `EMBEDDING_MODEL` кеш моделей сбрасывается,
  такие параметры помечены «требует переиндексации».
- `HYBRID_FUSION` поддерживает `rrf` (по умолчанию) и `dense` — во втором случае
  BM25-канал не используется, а candidates берутся только из векторного поиска.
- В кабинете есть карточка «Оценка качества»: запуск прогона по датасету
  `data/eval/dataset.json` в фоне (`GET /api/admin/eval`,
  `POST /api/admin/eval/start`), показ context_recall, доли ключевых слов,
  grounded_rate и разбивки по вопросам; вариант «с RAGAS» считает ещё и
  верность ответа контексту (`make evaluate` и `make evaluate-ragas` делают то же
  из командной строки).

Задержка поиска на CPU: гибридный запрос ~5 с, rerank 10 кандидатов ~4 с.

| Параметр | По умолчанию | Смысл |
|----------|---------------|-------|
| `HYBRID_SPARSE` | `1` | включать BM25-канал (после переиндексации) |
| `HYBRID_CANDIDATES` | `12` | сколько кандидатов берёт каждый канал |
| `RERANKER_ENABLED` | `1` | переранжирование cross-encoder'ом |
| `RERANKER_MODEL` | `BAAI/bge-reranker-v2-m3` | модель reranker'а |
| `RERANKER_CANDIDATES` | `10` | сколько кандидатов оценивает reranker |
| `RERANKER_TOP_K` | `5` | сколько оставляет в промпт |
| `RERANKER_MAX_LENGTH` | `512` | максимум токенов на пару «запрос-фрагмент» |
| `SPARSE_MODEL` | `Qdrant/bm25` | sparse-модель fastembed |

Замер на `data/eval/dataset.json` (10 вопросов, `make evaluate`):
`context_recall` 0,4636 → 0,4659, `answer_keyword_hit_rate` 0,5569 → 0,5748.
На целевой проверке «должен найтись конкретный документ» hybrid+reranker находит
5 из 6 документов против 4 из 6 на одном только dense-поиске.

## Оценка качества

Эталонные вопросы — в `data/eval/dataset.json`:

```json
{"items": [{"question": "Как восстановить доступ к VPN?", "answer": "обратиться в ИБ"}]}
```

```bash
make evaluate        # grounded_rate, context_recall, hit_rate
make evaluate-ragas  # дополнительно faithfulness, answer_relevancy, context_precision
```

Отчёт пишется в `data/eval/report.json`. Тот же прогон запускается из кабинета:
вкладка «Настройки» → карточка «Оценка качества» (кнопки «Запустить оценку» и
«Запустить с RAGAS»); API: `GET /api/admin/eval`, `POST /api/admin/eval/start`
с `{"ragas": true}`.

## Тюнинг качества

| Параметр | Переменная | По умолчанию |
|----------|------------|--------------|
| Размер чанка | `CHUNK_SIZE` | 1000 |
| Перекрытие | `CHUNK_OVERLAP` | 150 |
| Число фрагментов в ответе | `RETRIEVE_TOP_K` | 5 |
| Модель эмбеддингов | `EMBEDDING_MODEL` | `intfloat/multilingual-e5-base` |
| Порог подстановки исправления | `CORRECTION_MATCH_THRESHOLD` | 0.86 |
| Примеров исправлений в промпте | `CORRECTION_EXAMPLES` | 2 |
| Вариантов запроса по синонимам | `SYNONYMS_MAX_VARIANTS` | 6 |
| Температура ответа | `LLM_TEMPERATURE` | 0.1 |

Для коротких FAQ уменьшите `CHUNK_SIZE` до 400–600 и `CHUNK_OVERLAP` до 80.
Для длинных регламентов увеличьте `RETRIEVE_TOP_K` до 8–10 и переходите
на `intfloat/multilingual-e5-large` (потребуется переиндексация, `EMBED_DIM`
должен совпадать с размерностью модели).

Если исправления админа подставляются слишком часто или слишком редко —
подкрутите `CORRECTION_MATCH_THRESHOLD` (0.8 — чаще, 0.9 — реже).

Словарь синонимов расширяет каждый запрос и увеличивает время поиска
пропорционально числу вариантов. Если качество не улучшается, поставьте
`SYNONYMS_MAX_VARIANTS=3` или удалите записи словаря; проверить эффект можно
через `make synonyms-expand Q="..."` и сравнение выдачи `POST /retrieve` с
синонимами и без них.

## Частые проблемы

- `Индекс документации пуст` — не выполнялась индексация либо `data/docs` пуст.
  Проверьте `curl -s localhost:8091/collection`.
- `401 Требуется вход` — запрос сделан без cookie сессии; сначала `POST /api/login`.
- `403 Недостаточно прав` — пользователь не администратор; выдайте роль `admin`
  в кабинете или через `PATCH /api/admin/users/{id}`.
- Вход не проходит после смены `ADMIN_PASSWORD` — переменные читаются только
  при пустой таблице пользователей. Сбросьте пароль через кабинет.
- Вкладка кабинета пустая или не работают кнопки — обновите страницу (Ctrl+F5):
  браузер мог закэшировать старую версию HTML.
- `400 При редактировании ответа обязательны документ и номера страниц` —
  выберите документ в списке и укажите страницы (например `12-15`), затем
  нажмите «Подставить текст страниц».
- `404 Документ не найден в data/docs` — в выпадающем списке нет такого имени;
  проверьте, что файл лежит в `data/docs` или `data/extracted`.
- Исправление не срабатывает на вопрос — скорее всего, схожесть ниже
  `CORRECTION_MATCH_THRESHOLD`; проверьте порог или отключите исправление.
- `status: error` в `/reindex` — активный индекс не тронут, смотрите поле
  `error`; после исправления запустите `make reindex` ещё раз.
- Поиск не находит документы после смены `EMBEDDING_MODEL` или `CHUNK_SIZE` —
  выполните `make reindex`.
- Долгий первый запуск — скачивается модель эмбеддингов (~1.1 ГБ) в
  `app/.cache`.
- OOM на 7B в Ollama — используйте `qwen2.5:3b-instruct` или внешний API.
- Промты не соответствуют документации — правьте их в кабинете (вкладка «Стартовые промты»)
  состав источников: `curl -s localhost:8091/prompts | jq`.
- Долгая индексация — увеличьте `INGEST_WORKERS` и `OMP_NUM_THREADS` под число
  ядер, поднимите `EMBED_BATCH`.
- Обход сайтов идёт очень долго — снизьте `WEB_CRAWL_MAX_PAGES`, поднимите
  `WEB_CRAWL_DELAY_MS`; страницы сайтов заменяют предыдущие целиком, поэтому
  повторный обход безопасен.
- В источниках встречаются файлы вида `ESConsole/__.txt` — это распакованные
  CHM в `data/extracted`, у которых заголовок страницы состоял из непечатных
  символов — уберите каталог (не забудьте `--force-recreate` у контейнера).
- После удаления или замены файлов в `data/docs` индекс не меняется сам — нужен
  `make reindex` (или кнопка на вкладке «Индексация»).
