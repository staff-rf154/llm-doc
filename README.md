# RAG-ассистент по внутренней документации company

Локальный RAG-пайплайн на CPU: индексация документации (PDF/DOCX/TXT/MD/HTML/CHM)
в Qdrant эмбеддингами `multilingual-e5-base`, поиск по векторам, генерация ответа
с цитированием источников, веб-чат с авторизацией и кабинет администратора:
пользователи, оценки ответов, исправления ответов со ссылкой на страницы
документации, словарь синонимов, статистика запросов и управление индексацией.

## Как это работает

```
data/docs/*.pdf, *.chm ──► chm_extract.py ──► data/extracted/*.txt
                                        │
                                        ▼
                       loaders.py → chunking → multilingual-e5-base
                                        │
                                        ▼
                    Qdrant: docs_v<timestamp>  ──alias swap──►  alias "docs"
                                        │
   вопрос ──► исправления админа (Qdrant: corrections)  ─┐     │
           └► словарь синонимов (расширение запроса) ──┐  │
                                                        ▼  ▼
                                          retrieval + LLM + цитаты [doc:chunk]
                                                        │
                                                        ▼
                                    app.db: вопрос, ответ, ссылка на страницу,
                                            оценка пользователя
```

1. **Загрузка.** `loaders.py` читает PDF (pypdf), DOCX, TXT, MD, HTML; из CHM
   предварительно распаковывается текст (`chm_extract.py`, 7z + BeautifulSoup).
2. **Чанкинг.** `ingest.split_text` режет текст `RecursiveCharacterTextSplitter`
   с перекрытием (`CHUNK_SIZE` / `CHUNK_OVERLAP`).
3. **Эмбеддинги.** `vectorstore.embed_passages` кодирует чанки моделью
   `intfloat/multilingual-e5-base` на CPU (префикс `passage: `), запросы —
   с префиксом `query: `, векторы нормализованы, косинусная метрика.
4. **Хранилище.** Qdrant, коллекция версионированная `docs_v<YYYYmmdd-HHMMSS>`,
   имя `docs` — алиас, через который идёт весь поиск.
5. **Расширение запроса.** `synonymdb.expand` подставляет синонимы из отдельной
   БД `data/synonyms/synonyms.db`, варианты ищутся в Qdrant, результаты
   объединяются и обрезаются до `RETRIEVE_TOP_K`.
6. **Исправления.** Отдельная БД `app.db` (таблица `corrections`) и коллекция
   Qdrant `corrections` с эмбеддингами вопросов; при заданной похожести
   исправленный ответ отдаётся вместо сгенерированного — вместе со ссылкой
   на документ и страницу.
7. **Retrieval + генерация.** `rag.retrieve` берёт `RETRIEVE_TOP_K` фрагментов,
   `rag.ask` собирает промпт с цитатами и обращается к LLM (Ollama или внешний
   OpenAI-совместимый API). Флаг `grounded` показывает, не был ли ответ
   отказом («нет информации»).
8. **Журнал.** Каждый вопрос и ответ пишутся в `app.db` с пользователем,
   временем, источниками, ссылкой и оценкой.

## Требования

- Docker + Docker Compose v2
- ~5 ГБ RAM для `qwen2.5:3b-instruct` + эмбеддинги, ~8 ГБ для 7B
- ~1 ГБ на диске под веса эмбеддингов (в т. ч. кэш `./app/.cache`)
- от 8 CPU-ядер для комфортной индексации (параллелизм настраивается)

## Быстрый старт

```bash
cp .env.example .env

# задать администратора (создаётся при первом старте)
# ADMIN_USERNAME=admin
# ADMIN_PASSWORD=сильный-пароль

# 1. документация в data/docs (PDF/DOCX/TXT/MD/HTML/CHM)
# 2. поднять qdrant + ollama + api
make up

# 3a. первичная индексация из CLI (блокирует индекс на время работы)
make ingest

# 3b. либо индексация в фоне, поиск продолжает работать
make reindex

# 4. открыть чат и войти
# http://localhost:8091/
```

При первом старте автоматически создаются три БД:

| БД | Путь | Что хранит |
|----|------|------------|
| состояние индексации | `data/index_state/index.db` | срезы прогресса и незавершённые запуски |
| пользователи и журнал | `data/app/app.db` | учётные записи, сессии, вопросы и ответы, оценки, исправления |
| синонимы | `data/synonyms/synonyms.db` | словарь синонимов |

Прогресс фоновой индексации: `make reindex-status` или `GET /reindex`.
Кабинет администратора: `http://localhost:8091/admin`.

## Пользователи и авторизация

- Логин/пароль, сессия хранится в HttpOnly cookie `sid` (срок 14 дней).
- Пароли — PBKDF2-SHA256, 200 000 итераций, индивидуальная соль.
- Роли: `user` (чат, оценки) и `admin` (кабинет администратора).
- Первый администратор создаётся при первом старте приложения из переменных
  `ADMIN_USERNAME` / `ADMIN_PASSWORD` — только если таблица пользователей пуста.
- Без входа недоступны `/chat`, `/ask` и все эндпоинты `/api/admin/*`.

```bash
curl -s -c cookie.txt -X POST localhost:8091/api/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"..."}'

curl -s -b cookie.txt localhost:8091/api/me
curl -s -b cookie.txt -X POST localhost:8091/api/logout
```

Таблицы в `data/app/app.db`:

| `sessions` | `token`, `user_id`, `created_at`, `expires_at` |
| `requests` | `id`, `user_id`, `username`, `question`, `answer`, `grounded`, `corrected`, `doc_name`, `doc_pages`, `doc_ref`, `sources`, `latency_ms`, `created_at` |

## Оценки ответов и статистика

- Под каждым ответом в чате — 👍/👎 и поле комментария; оценка пишется в `ratings`
  и привязана к `request_id` из ответа ассистента.
- Статистика в кабинете: всего запросов, лайков, дизлайков; сколько запросов
  приходится на каждого пользователя; распределение по дням; самые частые вопросы
  с разбивкой по оценкам.
- Ответы, пришедшие из исправлений администратора, помечены в списке запросов
  значком «исправленный» вместе со ссылкой на страницу документа.

```bash
curl -s -b cookie.txt localhost:8091/api/admin/stats | jq
curl -s -b cookie.txt 'localhost:8091/api/admin/requests?vote=down' | jq
```

## Исправления ответов

Админ может создать исправление по конкретному вопросу или отредактировать
ответ прямо в списке запросов. Исправления хранятся в отдельной БД
(`data/app/app.db`, таблица `corrections`) и индексируются в отдельной коллекции
Qdrant `corrections` эмбеддингами вопросов.

**При создании и при любом редактировании ответа обязательны документ и номера
страниц.** Админ выбирает документ из списка файлов `data/docs` и указывает
страницы (`12-15`, `7, 12-15`), после чего кнопка «Подставить текст страниц»
извлекает текст этих страниц из PDF (через pypdf) в поле ответа как основу —
дальше админ правит его вручную. Текстовые документы режутся на условные
страницы по символу разрыва страницы.

Ссылка хранится в исправлении (`doc_name`, `doc_pages`, `doc_ref`) и показывается
пользователю под ответом: «Документация: FileAuditor_installation.pdf, с. 3».
Без заполненных полей API отклоняет правку с `400`.

Как исправления влияют на ответы:

1. При каждом вопросе ищется похожий вопрос среди активных исправлений.
2. Если косинусная схожесть ≥ `CORRECTION_MATCH_THRESHOLD` (по умолчанию `0.86`),
   пользователю сразу отдаётся исправленный ответ с пометкой
   «Ответ скорректирован администратором» и ссылкой на страницу документа —
   генерация LLM не вызывается.
3. Иначе до `CORRECTION_EXAMPLES` похожих исправлений добавляются в промпт как
   примеры правильного ответа и стиля.
4. Статус `disabled` исключает исправление из подбора, `active` возвращает его.

Индекс исправлений синхронизируется при старте приложения и при каждом
изменении через API.

```bash
# список документов для ссылки
curl -s -b cookie.txt localhost:8091/api/admin/documents | jq

# текст страниц — основа ответа
curl -s -b cookie.txt -X POST localhost:8091/api/admin/documents/pages \
  -H 'Content-Type: application/json' \
  -d '{"doc_name":"FileAuditor_installation.pdf","doc_pages":"12-15"}' | jq

# создать исправление
curl -s -b cookie.txt -X POST localhost:8091/api/admin/corrections \
  -H 'Content-Type: application/json' \
  -d '{"question":"Как установить FileAuditor?","answer":"...",
       "doc_name":"FileAuditor_installation.pdf","doc_pages":"12-15"}'

# отключить
curl -s -b cookie.txt -X PATCH localhost:8091/api/admin/corrections/1 \
  -H 'Content-Type: application/json' -d '{"status":"disabled"}'
```

## Словарь синонимов

Отдельная БД `data/synonyms/synonyms.db` (в контейнере
`/data/synonyms/synonyms.db`), таблица `synonyms`:

| Поле | Назначение |
|------|------------|
| `term` | термин (первичный ключ, в нижнем регистре) |
| `synonyms` | синонимы через запятую |
| `author` | кто изменил |
| `updated_at` | время изменения |

Словарь используется для расширения поискового запроса: перед обращением к
Qdrant вопрос разбивается на слова, для найденных терминов строятся варианты с
подстановкой синонимов (учёт падежных форм: «лицензию» → термин «лицензия»;
многословные термины вроде «рабочее время» ищутся как фразы). Варианты
запрашиваются параллельно, результаты объединяются по `(source, chunk)` с
выбором лучшего скора, и только после этого обрезаются до `RETRIEVE_TOP_K`.
Варианты, в которых смысл уже покрыт (синоним присутствует в вопросе),
отбрасываются. Кэш словаря — `SYNONYMS_CACHE_TTL` секунд, сбрасывается при
изменении через API.

При первом старте каталог наполняется стартовым набором по терминологии
company (`app/synonyms.py`, 33 термина), дальше его правит администратор
на вкладке «Синонимы»: правка по месту, добавление термина, массовый импорт
по строкам `слово — синоним1, синоним2` и проверка, какие варианты запроса
получатся для произвольного вопроса.

```bash
make synonyms               # текущий словарь
make synonyms-expand Q="как активировать лицензию"
make seed-synonyms          # пересоздать стартовый каталог
```


## Что умеет ассистент

На вопросы вида «что ты умеешь», «чем ты можешь помочь», «какие у тебя
возможности» ассистент отвечает без обращения к LLM — фиксированным списком
возможностей (`app/capabilities.py`) плюс примерами вопросов из БД промтов,
подобранными по составу индекса. Тот же перечень показан карточкой «Что я умею»
на главной странице чата, а также продублирован в `SYSTEM_PROMPT`.

Перечень:

- работа с текстом и информацией: ответы на вопросы, объяснение сложных тем,
  написание, редактирование, сокращение и перевод текстов, анализ документов,
  статей и договоров, помощь с письмами, резюме, отчётами и презентациями;
- база знаний company: поиск по проиндексированной документации с
  показанием источников;
- ограничения: ассистент не выходит в интернет, не выполняет действия в
  системах и не выдумывает факты.

## Фоновая переиндексация без простоя

Ключевая особенность системы: переиндексация **никогда не очищает рабочий
индекс** и не блокирует поиск.

1. Чанки пишутся в **новую** коллекцию `docs_v<YYYYmmdd-HHMMSS>` — активный
   индекс `docs` в этот момент не трогается.
2. Поиск (`/retrieve`, `/ask`, `/chat`) идёт через алиас `docs` на старую
   коллекцию и отвечает как обычно.
3. Когда все точки загружены, алиас `docs` переключается на новую коллекцию
   (атомарно, `update_collection_aliases`).
4. Только после переключения удаляется предыдущая коллекция.

Если индексация упала на любом шаге до переключения — алиас остаётся на старой
коллекции, поиск продолжает работать, в статусе будет `error` с текстом ошибки.

```bash
make reindex         # POST /reindex — запуск в фоне, ответ сразу (202)
make reindex-status  # GET /reindex  — статус и прогресс
```

```json
{
  "status": "running",
  "started_at": "2024-05-14T10:12:03",
  "done": 2432,
  "total": 6138,
  "collection": "docs_v20240514-101203",
  "target": "docs",
  "collection_info": {"exists": true, "points": 6138, "status": "green"}
}
```

Поля статуса:

| Поле | Значение |
|------|----------|
| `status` | `idle` / `running` / `paused` / `done` / `error` |
| `done`, `total` | загружено и всего чанков |
| `skipped_files` | файлов, полностью загруженных ранее |
| `failed_files` | список файлов с ошибкой чтения или загрузки |
| `collection` | версия новой коллекции |
| `started_at`, `finished_at`, `paused_at` | время старта, завершения, паузы |
| `error` | текст ошибки, если `status = error` |
| `collection_info` | состояние коллекции, на которую сейчас ссылается алиас |

Повторный `POST /reindex`, пока идёт работа, возвращает `202` и
`detail: переиндексация уже выполняется` — параллельных задач не будет.

Те же операции доступны администратору на вкладке «Индексация».

## Срез прогресса, возобновление и пауза

Индексация не начинается заново после падения или перезапуска сервера.

**Состояние** хранится в отдельной БД `data/index_state/index.db` (SQLite,
в контейнере `/data/index_state/index.db`):

| Таблица | Содержимое |
|---------|------------|
| `runs` | `collection`, `status` (`running`/`paused`/`interrupted`/`done`/`error`), `started_at`, `finished_at`, `error` |
| `file_progress` | `collection`, `source_key`, `size`, `mtime`, `chunks`, `done`, `updated_at` |

Механика:

- каждые `INGEST_CHECKPOINT_EVERY` чанков (по умолчанию 64) делается **срез** —
  в БД пишется, сколько чанков текущего файла уже загружено;
- при следующем запуске файлы с не изменившимися `size`/`mtime` пропускаются,
  изменённые переиндексируются полностью;
- дополнительно сверяется сам Qdrant: номера уже загруженных чанков читаются
  из payload, поэтому даже без БД индексация продолжит с места обрыва;
- ID точек детерминированы (`uuid5(source:chunk)`), поэтому дозагрузка
  идемпотентна — дубликатов не появляется;
- если запись о прогрессе потеряна, но осталась незавершённая версия коллекции
  `docs_v<ts>`, индексация продолжит её, а не создаст новую.

**Пауза**:

```bash
make reindex-pause    # POST /reindex/pause — дописывает текущий батч и встаёт
make reindex-resume   # POST /reindex/resume — продолжает с последнего среза
make reindex          # если индексация на паузе, тоже продолжает её
```

Значения `status`: `idle`, `running`, `paused`, `done`, `error`.

## Ускорение индексации

Индексация идёт в несколько потоков:

| Параметр | Переменная | По умолчанию | Смысл |
|----------|------------|--------------|-------|
| Потоки индексации | `INGEST_WORKERS` | `8` | сколько файлов обрабатывается одновременно (чтение, чанкинг, запись в Qdrant) |
| Потоки CPU | `OMP_NUM_THREADS` | `12` | потоки torch при расчёте эмбеддингов |
| Размер батча эмбеддингов | `EMBED_BATCH` | `32` | сколько текстов кодируется за раз |
| Точек в одном upsert | `INGEST_BATCH_SIZE` | `64` | размер батча записи в Qdrant |

Практика: 12 350 чанков на 16 ядрах — около 20 минут вместо ~2 часов при
`OMP_NUM_THREADS=4` и однопоточной индексации. Эмбеддинги считаются под
блокировкой, поэтому `INGEST_WORKERS` даёт прирост за счёт совмещения I/O,
чанкинга и записи с расчётом эмбеддингов.

## Стартовые промты

Стартовые вопросы хранятся в **отдельной БД** — SQLite
`data/prompts/prompts.db` (в контейнере `/data/prompts/prompts.db`).

| Поле | Назначение |
|------|------------|
| `id` | порядок выдачи |
| `text` | текст промта (уникальный) |
| `product` | продукт company (КИБ, Файловый аудитор, SIEM, ProfileCenter…) |
| `keywords` | ключевые слова для сопоставления с документами индекса |
| `source_url` | ссылка на источник (документ на docs.example.org или раздел сайта) |
| `active` | показывается ли промт в чате |
| `created_at` | дата добавления |

Каталог наполнен по результатам анализа сайта <https://example.org/>
(разделы «Продукты», «Решения», «Бизнес-задачи», «Контроль сотрудников») и
привязан к документации `docs.example.org`, которая лежит в индексе:
СёрчИнформ КИБ/DLP, ИИ-Ассистент, Файловый аудитор, SIEM (включая интеграцию с
ГосСОПКА и правила корреляции), Центр профилирования, контроль времени,
веб-аналитика, Search Server, EndpointController, AAServer, ESHub, DataCenter,
лицензирование, эксплуатация и диагностика.

Выдача динамическая: `GET /prompts` сначала выбирает промты, чьи `keywords`
встречаются среди реально проиндексированных документов, затем добавляет
универсальные продуктовые вопросы с сайта, и отдаёт первые `PROMPTS_MAX`.
Результат кэшируется на `PROMPTS_CACHE_TTL` секунд.

```bash
make seed-prompts   # пересоздать каталог в БД
make prompts        # посмотреть текущую выдачу
```

При пустой БД каталог создаётся автоматически при старте приложения
(`PROMPTS_SEED_ON_START=1`).

## Веб-интерфейс

`http://<host>:8091/` — вход, чат с потоковой генерацией (SSE), история диалога,
карточка «Что я умею», динамические стартовые промты, раскрываемые источники под
каждым ответом (клик по фрагменту разворачивает его полностью), оценки
👍/👎 с комментарием и ссылкой на страницу документа, если ответ пришёл
из исправления администратора.

Примеры:

```bash
# вход и ответ с цитатами
curl -s -c cookie.txt -X POST localhost:8091/api/login \
  -H 'Content-Type: application/json' -d '{"username":"admin","password":"..."}'

curl -s -b cookie.txt -X POST localhost:8091/ask \
  -H 'Content-Type: application/json' \
  -d '{"question":"Как восстановить доступ к VPN?"}' | jq

# SSE-чат с историей
curl -N -b cookie.txt localhost:8091/chat \
  -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"Что такое SIEM?"}]}'
```

Формат ответа `/ask`:

```json
{
  "answer": "...",
  "grounded": true,
  "corrected": false,
  "request_id": 42,
  "reference": null,
  "sources": [
    {"source": "SIEM_help.pdf", "chunk": 12, "score": 0.8731, "text": "..."}
  ]
}
```

Если ответ взят из исправления администратора, `corrected` = `true`, `sources`
пустой, а `reference` содержит ссылку:

```json
{
  "answer": "...",
  "grounded": true,
  "corrected": true,
  "reference": {
    "doc_name": "FileAuditor_installation.pdf",
    "doc_pages": "12-15",
    "doc_ref": "FileAuditor_installation.pdf, с. 12-15"
  },
  "sources": []
}
```

Формат ответа `/chat` (SSE-события):

| Тип | Данные |
|-----|--------|
| `token` | очередной фрагмент текста ответа |
| `prompts` | примеры вопросов (ответ на «что ты умеешь») |
| `sources` | найденные фрагменты с цитатами |
| `reference` | документ и страницы, если ответ скорректирован администратором |
| `request` | `request_id` для оценки |
| `meta` | `grounded` и `corrected` |
| `error` / `done` | ошибка генерации / конец потока |

## Локальная генерация на CPU

```bash
make pull-llm LLM_MODEL=qwen2.5:3b-instruct
```

По умолчанию `qwen2.5:3b-instruct` (~2 ГБ RAM) — подходит для сервера с 5 ГБ
оперативной памяти. При 8+ ГБ можно взять `qwen2.5:7b-instruct`
(`make pull-llm LLM_MODEL=qwen2.5:7b-instruct`) — качество ответов по
русскоязычным мануалам выше, но скорость генерации падает.

Либо внешний API (OpenAI-совместимый):

```bash
LLM_BASE_URL=https://api.openai.com/v1
LLM_API_KEY=sk-...
LLM_MODEL=gpt-4o-mini
```

## Тюнинг качества

| Параметр | Переменная | По умолчанию |
|----------|------------|--------------|
| Размер чанка | `CHUNK_SIZE` | 1000 |
| Перекрытие | `CHUNK_OVERLAP` | 150 |
| Число фрагментов в ответе | `RETRIEVE_TOP_K` | 5 |
| Модель эмбеддингов | `EMBEDDING_MODEL` | `intfloat/multilingual-e5-base` |
| Порог подстановки исправления | `CORRECTION_MATCH_THRESHOLD` | 0.86 |
| Примеров исправлений в промпте | `CORRECTION_EXAMPLES` | 2 |
| Вариантов запроса по синонимам | `SYNONYMS_MAX_VARIANTS` | 6 |

Для коротких FAQ уменьшите `CHUNK_SIZE` до 400–600 и `CHUNK_OVERLAP` до 80.
Для длинных регламентов увеличьте `RETRIEVE_TOP_K` до 8–10 и переходите
на `intfloat/multilingual-e5-large` (потребуется переиндексация, `EMBED_DIM`
должен совпадать с размерностью модели).

Если исправления админа подставляются слишком часто или слишком редко —
подкрутите `CORRECTION_MATCH_THRESHOLD` (0.8 — чаще, 0.9 — реже).

Словарь синонимов расширяет каждый запрос и увеличивает время поиска
пропорционально числу вариантов. Если качество не улучшается, поставьте
`SYNONYMS_MAX_VARIANTS=3` или отключите словарь, удалив его записи; проверить
эффект можно через `make synonyms-expand Q="..."` и сравнение выдачи
`POST /retrieve` с синонимами и без них.

## Частые проблемы

- `Индекс документации пуст` — не выполнялась индексация либо `data/docs` пуст.
  Проверьте `curl -s localhost:8091/collection`.
- `401 Требуется вход` — запрос сделан без cookie сессии; сначала `POST /api/login`.
- `403 Недостаточно прав` — пользователь не администратор; выдайте роль `admin`
  в кабинете или через `PATCH /api/admin/users/{id}`.
- `400 При редактировании ответа обязательны документ и номера страниц` —
  выберите документ в списке и укажите страницы (например `12-15`), затем
  нажмите «Подставить текст страниц».
- `404 Документ не найден в data/docs` — в выпадающем списке нет такого имени;
  проверьте, что файл лежит в `data/docs` или `data/extracted` и перезагрузите
  страницу кабинета.
- Исправление не срабатывает на вопрос — скорее всего, схожесть ниже
  `CORRECTION_MATCH_THRESHOLD`; проверьте подбор через `GET /synonyms`
  и порог, либо отключите исправление, чтобы оно не попадало в промпт.
- Вход не проходит после смены `ADMIN_PASSWORD` — переменные читаются только
  при пустой таблице пользователей. Сбросьте пароль через кабинет.
- `status: error` в `/reindex` — активный индекс не тронут, смотрите поле
  `error`; после исправления запустите `make reindex` ещё раз.
- Поиск не находит документы после смены `EMBEDDING_MODEL` или `CHUNK_SIZE` —
  выполните `make reindex`.
- Долгий первый запуск — скачивается модель эмбеддингов (~1.1 ГБ) в
  `app/.cache`.
- OOM на 7B в Ollama — используйте `qwen2.5:3b-instruct` или внешний API.
- Промты не соответствуют документации — `make seed-prompts` и проверьте
  состав источников: `curl -s localhost:8091/prompts | jq`.
- Долгая индексация — увеличьте `INGEST_WORKERS` и `OMP_NUM_THREADS` под число
  ядер, поднимите `EMBED_BATCH`.
